## 它和错题追踪器有什么不一样

两个追踪器管的不是一回事：

| | 错题追踪器 | 工具链坑追踪器 |
|---|---|---|
| 管什么 | Python 概念题 | git / 网络 / Windows / AI 工具 |
| 怎么用 | **每周四出卷考** | **查得到**就行，不用定时 |
| 目标 | 复习到不再犯 | 忘了别再排查半小时 |
| 判定 | 连对 2 次才算掌握 | 踩坑次数 +1 就往前排 |

**为什么不用每周考**：git 推不上去这种事**不需要定期复习** —— 要么遇到了就查，要么就没事。硬要每周考一遍纯属浪费。

**但它有个致命特点**：一旦忘了，**就要重新排查半小时**。这半小时不是学习，是纯粹的重复劳动。

## 功能

| 命令 | 作用 |
|---|---|
| `ls` | 列出全部坑（按踩坑次数排序） |
| `stats` | 统计概览 + 最隐蔽的坑 TOP + 标签分布 |
| `show T03` | 看某条详情（症状 / 原因 / 解法 / 流水） |
| `add "标题" "症状" "原因" "解法" "标签1,标签2"` | 登记新坑 |
| `hit T03 "备注"` | 又踩了一次 → 次数 +1 |
| `fix T03 "新解法"` | 追加一个解法 |
| `tag T03 "git,网络,排查"` | 改标签（整组替换） |
| `render` | 重新生成 `工具链坑.md` |

## 技术点

- **踩坑次数越高排得越前** —— 次数多说明这个坑隐蔽、说明它还会再咬人（跟错题追踪器的 `occurrences` 同一个思路）
- **`solutions` 字段可以追加新解法** —— 同一个坑在不同环境下解法可能不同，不是覆盖，是追加
  ```python
  # 有 solutions 字段可以追加"新的解法"（同一个坑，不同环境可能不同解法）
  ```
- **标签分隔符三种都认**：英文逗号 `,` / 中文逗号 `，` / 中文顿号 `、` —— 随手记的时候不用管格式
- **`tag` 命令整组替换**（不是追加）—— 改标签就是改这一组的完整归属
- **JSON 持久化 + 自动渲染 Markdown**：`save()` 里直接调 `render()`，所以 `工具链坑.md` 永远和 JSON 同步，不用手动同步

## 我踩过的坑（这里最值钱）

### T10：执行即写入的脚本，不能拿来"测试"

> 执行即写入的脚本不能拿来"测试"——我为了验证路径改对没，把错题池污染了

这条是**我自己给自己挖的坑**，而且性质很恶劣：

`错题追踪器.py` 的 `save()` 函数是**一执行就写盘**的。我想验证"路径算对了没"，就直接跑了一遍脚本 —— 结果它顺手 `save()` 了，把我的错题池**改乱了**。

**错在哪**：我在验证"路径对不对"这个**只读问题**，用的却是一个**带副作用**的工具。跑一下就写盘，我事先完全不知道。

**现在的做法**：验证路径用 `show` / `ls` / `stats` 这类**只读命令**，绝不拿会写盘的动作当探针。

> 这一条跟 Python 语法一点关系没有，但它让我第一次意识到 —— **"跑一下看看"本身也可能是有代价的操作**。

### T09：预览本地 xlsx，原文件从磁盘消失了

> 预览本地 xlsx 后原文件从磁盘消失，只剩备份在

用工具预览一个本地 xlsx，**原文件不见了**，只剩备份。

这条让我改了习惯：**任何"预览/转换"类操作之前，先确认备份存在**。

### T03：两条通道，要分开测

> 「网页打不开」不等于「git 推不上去」—— 两条通道要分开测

这是唯一一条**踩了 3 次**的坑，也是最有价值的一条。

浏览器能不能打开 GitHub，和 git 能不能推上去，是**两条独立的链路** —— 前者走 HTTP 代理，后者走 git 自己的 HTTP/2 + 认证层。**curl 探测返回 200，不代表 `git push` 一定能成功。**

10-28 又掐了一次，我靠这条避免了把时间浪费在"再换个 IP 试试"上。

### T12：四步诊断法（今天新学的）

> GitHub 推送失败的四步诊断法 —— 别急着换 IP

今天下午 GitHub 又掐了一次，`git push` 报 `Connection was reset`。前 20 分钟我都在换 IP —— **换错方向了**。

失败原因分四层，不按顺序排查就瞎试：

| 步 | 检查 | 本次结果 | 结论 |
|---|---|---|---|
| ① | 测别的站点（百度/Gitee/GitCode/B站） | 全部 200 | 网络正常，**只有 GitHub 被掐** —— 别去改路由器 |
| ② | `nslookup github.com` | **超时** | DNS 被阻。但 git 走锁定 IP 时不受影响，照样能 push |
| ③ | `env \| grep proxy` | 有 `127.0.0.1:54880` | WorkBuddy 注入的代理只放行特定域名，对 GitHub 无效 —— 脚本里 unset 掉是**对的** |
| ④ | 扫 IP 池 | 原 6 个 IP **全部 TCP 握手失败**（curl 返回 000） | GitHub 封 IP 是**整段随机**的 → 扩池到 12 个才有用，换顺序没用 |

**最关键的一条**：`curl 探测 200 ≠ git push 成功`（中间隔着 git 自己的 HTTP/2 + 认证层）→ **探测阶段和推送阶段必须各自独立重试**。

**顺带改了两个 push.sh 的真 bug**：
- 第 2 步 `ls-remote` 失败就 `exit 1` —— 可推送阶段本来就有独立换 IP 重试，脚本却提前退出了。改成提示后继续
- 第 5 步 `git push 2>/dev/null` 吞报错 —— 现在捕获到 `LAST_ERR` 再打印，并给出「链路问题 vs 认证问题」的分诊指引

> 这条入库的意义：**下次再掐，我打开这份文档就能按顺序走，不用再从零推 40 分钟。**
