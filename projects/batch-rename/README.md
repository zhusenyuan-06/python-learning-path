# 批量重命名文件脚本

把某个目录下，文件名里包含「旧片段」的文件，改成包含「新片段」的名字。

**当前状态**：✅ **任务 4（链式改名）已完成** —— 11-04 晚搭骨架 → 11-04 晚写完 6 个核心函数 → 11-06 支持链式改名（两阶段）。
**实跑 20 个场景的回归，全过（0 失败）**。

---

## 用法

```bash
# 1. 先看计划（什么都不改）—— 强烈建议每次都先跑这步
python batch_rename.py D:/照片 _v1 _v2 --ext .jpg

# 2. 确认没问题了，再真改
python batch_rename.py D:/照片 _v1 _v2 --ext .jpg --apply

# 3. 改错了，撤销（撤销模式不需要目录和片段，只要日志文件）
python batch_rename.py --undo 改名日志.log
```

| 参数 | 说明 |
|---|---|
| `目录` | 要处理的目录（位置参数） |
| `旧片段` | 文件名里要被替换的片段（位置参数） |
| `新片段` | 替换成的新片段（位置参数） |
| `--ext .txt` | 只改这个扩展名的文件（默认全部） |
| `--suffix` | 只改主体名**以旧片段结尾**的文件（`报告_v1` 改，`报告_v1_备份` 不改） |
| `--apply` | 真正执行（**不加就只打印计划**） |
| `--undo 日志` | 按日志撤销（**不需要那 3 个位置参数**） |

> **在 PyCharm 里点【运行】按钮会看到什么**：
> 会出现一段中文提示告诉你需要 3 个参数 —— 因为点运行时命令行是空的，
> 而这个脚本**必须**告诉它「改哪个目录、替换什么」。
> 想在 PyCharm 里直接跑，就在【运行配置 → 参数】里填上：
> `D:/你的目录 _v1 _v2 --ext .txt`
>
> **命令行参数和 GUI 是两回事** —— 这个脚本本质是个命令行工具，
> 直接在终端敲 `python batch_rename.py ...` 最自然。

## 安全设计三件套

批量改名是**不可逆操作**，所以这个脚本的重点不是「怎么调 `rename()`」，是「**怎么保证不把文件搞坏**」。

### ① dry-run 默认开

不加 `--apply` 就只打印「旧名 → 新名」的计划表，什么都不改。

### ② 冲突预检

目标名已经存在 → **跳过 + 报告，绝不覆盖**。

为什么必须自己检查，不能靠 `rename()` 报错？因为 `Path.rename()` 在目标已存在时的行为**跨平台不一致**：

| 平台 | 行为 |
|---|---|
| Windows | 抛 `FileExistsError`（拒绝覆盖） |
| Linux | **静默覆盖**，原文件内容直接没了 |

同一个脚本在 Windows 上给你报错，在别人 Linux 上把文件吞了。

### ③ 操作日志 + 撤销

每次真改名都记一份「旧名 → 新名」日志，`--undo` 可以改回去。

## 三个已实测的坑

### 坑 1：新片段带路径分隔符 → 文件会被静默搬进子目录

用 `with_name()` 拼 → `ValueError: Invalid name 'sub/a.txt'`（报错明确）。
用 `目录 / 新名字` 拼 → **如果目标目录恰好存在，文件会被真的搬进去**：

```
根目录剩: ['sub']
sub 里: ['a.txt']
```

这就是「批量改名」悄悄变成「批量搬家」—— 不报错、不提示、文件位置变了。
→ **必须提前挡**：`if "/" in 新片段 or "\\" in 新片段: 报错退出`

### 坑 2：文件被别的程序占着 → `PermissionError: [WinError 32]`

VSCode 打开着 / OneDrive 正在同步 / 杀毒软件正在扫。

这跟 todo-cli 里 `os.replace` 踩的 WinError 32 是**同一个坑**（Windows 特有的文件锁）。

→ 每个文件单独 `try/except`，一个失败不影响后面的。

### 坑 3：边遍历边改名 → 会漏文件

实测 `iterdir()` 和 `glob()` 返回的都是**生成器**。一边迭代一边改名，目录内容在变，迭代器可能跳过元素。

→ 必须先把要改的**全部收集成列表**，再动手。

## 链式改名：两阶段（已支持）

目录里有 `A.txt → B.txt`、`B.txt → C.txt` 这种「A 要改成 B，而 B 也要改成 C」的情况，
单阶段改会失败 —— 先改 A→B 时 B 还被原文件占着（`FileExistsError`）。

**两阶段怎么解决**：

```
阶段 1：所有文件【先】改成唯一临时名     A.txt→__tmp_a1b2.txt
         B.txt→__tmp_c3d4.txt
         （谁都不占谁的位置，不会撞车）

阶段 2：再【统一】从临时名改成目标名     __tmp_a1b2.txt→B.txt
         __tmp_c3d4.txt→C.txt
         （这时候目标位置全空着，改谁都行）
```

**关键设计**：一组是「全有或全无」的 —— 任何一个文件出问题，**整组回滚**，
不会出现「改了一半，文件名对不上」的烂摊子。

**撤销也是链式**：正着改是 `A→B、B→C`，倒回来撤是 `B→A、C→B` —— 一样互相占位。
所以撤销**复用同一套两阶段逻辑**，不另写一套。

## 已知限制

### ⚠️ 不递归子目录

只处理**一层**目录里的文件，子目录里的文件不动。这是刻意的设计（避免误改深层文件）。

### ⚠️ 两阶段改名的副作用

脚本在「阶段 1 改临时名」和「阶段 2 改目标名」之间崩了（断电 / Ctrl+C），
磁盘上会留下一堆 `__tmp_` 开头的文件。它们带原扩展名，人工改回来不难。
