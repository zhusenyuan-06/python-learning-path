# A 组 · 技术坑（4 条）

## A1. `dict.values()` 返回的是视图对象，永远为真

### ❌ 错误写法

```python
if d.values():          # 永远为 True（只要字典非空）
    return "有内容"
```

### ✅ 正确写法

```python
if all(v == 0 for v in d.values()):     # 全部为 0 才算空
    return "有内容"
```

### 📌 一句话记忆

> **视图对象本身永远为真，要判断内容得逐个看。**
> `d.values()` 返回的是「一个可以遍历字典值的对象」，不是「值的列表」。
> 一个非空对象 → `bool(对象)` 恒为 `True` → 这个 if 永远成立。

### 💭 我的反思


我当时犯了很低级的错误就是想用.values()来取出d里面的值，再做打算

## A2. 查值别查键

### ❌ 错误写法

```python
for ch in d:                    # ch 是「键」（一个字符）
    if d[ch] == 0:              # ← 这里如果写成 ch == 0 就错了
        ...
```

### ✅ 正确写法

```python
for ch, count in d.items():     # ch = 键（字符），count = 值（计数）
    if count == 0:              # 要比的是值
        ...
```

### 📌 一句话记忆

> **键是「是什么」，值是「有几个」。**
> `d` 的键是字符（`'a'`），`d['a']` 才是计数（数字）。
> 拿字符去和数字比 → `TypeError`。

### 💭 我的反思
其实这个.items():我已经用过很多次了，但是这一次还是没有想起来，说明记忆还是不够牢固

## A3. `split()` 对中文完全失效

### ❌ 错误写法

```python
words = text.split()        # 中文整段变成一个元素
```

### ✅ 正确写法

```python
import re
词模式 = re.compile(r'[\u4e00-\u9fa5]+|[a-zA-Z]+')
words = 词模式.findall(text)
```

### 📌 一句话记忆

> **`split()` 按空白切，中文没有空白 → 整句一块。**
> `split()` 是「按空白切」，不是「按词切」。中文必须靠正则。

### 💭 我的反思

## A4. `sorted` 给了 key 就只比 key

### ❌ 错误写法

```python
sorted(d.items(), key=lambda x: x[1], reverse=True)     # 次数相同的，顺序不定
```

### ✅ 正确写法

```python
sorted(d.items(), key=lambda x: (-x[1], x[0]))           # 次数降序 + 词升序
```

### 📌 一句话记忆

> **key 返回元组 → 元组逐项比，第一项相同才比第二项。**
> 负号放在次数上 = 降序；再拿词当第二项 = 同次数时按字典序，结果唯一。
> ⚠️ 注意：**元组 key 配 `reverse=True` 会把两个方向一起反转**，等于互相抵消 → 排序失效。

### 💭 我的反思

因为查清楚了，缺口判断反而更准：

- 原来的说法：「没用过 pytest」
- 实际的说法：「**从没写过任何自动化测试代码**」

→ 后者才是真正要补的东西。

### 📌 代价：同一个错误在三个地方同步复现

**一个错误在多处复现时，只改一处 = 没改。** 必须全仓 `grep` 那个错误字符串，确认清零。

# D 组 · 11-11 新增的技术坑（今天上午学的）

## D1. venv 隔离的真相：`include-system-site-packages = false`

### 📌 实测数据

```
全局（Anaconda base）：405 个包（pip freeze 口径）
你的新抽屉（.venv）  ：  6 个包
体积：14 MB（标准库谁也不 copy 一份）
```

### 📌 `pyvenv.cfg` 四行

```
home = D:\AAAA                              ← 母体解释器在哪
include-system-site-packages = false        ← ★★ 隔离总开关
version = 3.12.7
executable = D:\AAAA\python.exe
```

**第二行是命门**：`false` = 这个抽屉**没有权限**去看全局的包。
所以 `import requests` 报「找不到」—— **不是它不在你电脑上，是你的抽屉没权限去那儿拿。**

### 📌 意外收获（从自己的 traceback 里看出来的）

```
File "D:\AAAA\Lib\json\__init__.py"                            ← 全局母体的标准库
File "...\api-demo\.venv\Lib\site-packages\requests\models.py"  ← 抽屉里的第三方包
```

> **venv 只隔离「第三方包」（site-packages），标准库（json / os / sys / re…）还是共用母体的。**

### 📌 一句话记忆

> **「激活」不是隔离的必需品。**
> 隔离是 venv **本身**的属性（`include-system-site-packages = false` 干的活），
> 激活只是让你能直接敲 `python` 而不用打一长串路径。
> **工程上更推荐不激活**，直接用 `.\.venv\Scripts\python.exe`，谁用都一清二楚。

### 💭 我的反思

我一开始以为建 venv = 把整个 Python 复制一份进抽屉，所以看到它才 14MB 时还挺惊讶 —— 原来标准库是**共用母体那一份**，根本没复制。

最直观的一次是我自己的报错：`json` 来自 `D:\AAAA\Lib\json\`，`requests` 来自 `.venv\Lib\site-packages\` —— 两条路径同时出现在同一个 traceback 里，我才反应过来 venv 只隔离第三方包（site-packages），标准库还是母体的。

「抽屉没权限看全局的包」这句话，我会这么跟同学讲：**这个抽屉只认自己那几个包，别的抽屉的东西它拿不到** —— 干这活的是 `include-system-site-packages = false` 那一行。

「激活不是必需品」我是这么推出来的：不激活，直接敲 `.venv\Scripts\python.exe`，照样报「找不到 requests」。所以**隔离是抽屉自带的属性，激活只是让我能少打一串路径**，这俩根本不是一回事。我今天上午一开始就把这两件事混成一件了。

## D3. `requests.exceptions.JSONDecodeError` 是 `json.JSONDecodeError` 的子类

### 📌 实跑结论

```python
issubclass(requests.exceptions.JSONDecodeError, json.JSONDecodeError)
# → True
```

### 📌 为什么会有两个异常名

```
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
        ↑ 原始错误：标准库 json 解析失败
        ↓「During handling of the above exception, another exception occurred」
requests.exceptions.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
        ↑ requests 接住后重新包装（好处：消息里带上了是哪个 URL 出错）
```

**那句英文的意思**：「处理上一个异常的过程中，又发生了另一个异常」。

### 📌 一句话记忆

> **requests 包装过的异常，是标准库异常的子类 → 你写 `except json.JSONDecodeError` 一样能抓住。**
> 「Expecting value: line 1 column 1 (char 0)」= 第 0 个字符处解析不出值 → **因为 404 的正文是空的**（实测 `content-length: 0`）。

### 💭 我的反思

这种情况给我提了个醒，以后要尽量避免这种情况发生

## D5. CSV 三个坑（今天新踩）

### 坑 1：`encoding="utf-8-sig"` —— 给 Excel 看的文件必须带 BOM

#### 实测（正确模拟 Excel：先嗅探 BOM，没有再按 GBK 猜）

```
utf-8-sig → 嗅到 BOM → 按 UTF-8 解码 → '序号,日期,新闻内容,星期'  ✅
utf-8    → 无 BOM    → 按 GBK 猜    → '搴忓彿,鏃ユ湡,鏂伴椈鍐呭'    ❌ 乱码
```

**关键**：**Python 读回来两种都对** —— 因为 Python 明确知道自己用的什么编码。
Excel 靠 BOM 猜，没 BOM 就按本地 ANSI 猜 → 猜错就乱码。

> **这就是「静默错误」的完美案例**：同一个文件，Python 说没问题，Excel 说有问题，
> 而**你的代码从头到尾没报错**。

### 坑 2：`newline=""` —— 必须加在**写**的那一侧

#### 受控实验（2×2 组合矩阵，实跑）

| 写侧 | 文件含双 CR？ | 读回每行列数 |
|---|---|---|
| 有 `newline=""` | **False** | `[4, 4]` ✅ 干净 |
| 无 `newline=""` | **True** | `[4, 0, 4, 0]` ❌ 有空行 |

**机制**：`csv.writer` 自己会在每行末尾写 `\r\n`。
而 Windows 文本层看到 `\n` 就自动补一个 `\r`。
**写侧不给 `newline=""`，Windows 就帮你多补了一个 `\r`** → 文件里变成 `\r\r\n` → 读回来多一行空行。

> ⚠️ **修正一个我说错的地方**：我原话说「读侧也要加 `newline=""`」。
> 实测证明**读侧加不加都一样**（两种都读出 `[4,0,4,0]`），**真正有影响的是写侧**。
> 以实测为准。

### 坑 3：`ensure_ascii=False` —— 中文 JSON 必写

#### 实测

```
ensure_ascii=False : {"name": "张三", "city": "北京"}
ensure_ascii=True  : {"name": "\u5f20\u4e09", "city": "\u5317\u4acb"}
```

### 📌 一句话记忆

> **Python 内部随便用 utf-8，文件层面一律 `utf-8-sig` + `newline=""`。**
> 这是 Windows 生态的默认安全姿势。

### 📌 附带一个测试纪律

> **`ensure_ascii=False` 在纯英文数据上测不出来。**
> 我今天用 jsonplaceholder（全英文）测，发现文件里 **0 个非 ASCII 字符**，
> 开不开参数**输出完全一样** → **坑没显形，不是坑不存在**。
> **同一个参数，必须拿有中文的数据测。**
> 所以才把 06 换成全中文的 60s 接口。

### 💭 我的反思
我今天最大的收获是：**同一个参数，必须拿能显形的数据去测**。

`ensure_ascii=False` 我一开始在 jsonplaceholder 上测，全英文数据，开不开参数**输出完全一样**，
我差点就以为这个参数没用 —— 其实是**数据里根本没中文，坑显不出来**。
换成 60s 的全中文接口，坑立刻就现形了。

所以我现在的判断顺序是：
① 先想清楚**这个坑在什么数据下才会显形**；
② 挑**能让它显形**的数据去测；
③ 测出来「没区别」时，先怀疑是**测试数据不对**，不是怀疑参数没用。

还有一点：`newline=""` **只能加在写的那一侧** —— 我原以为读侧也要加，
受控实验跑完才发现读侧加不加都一样，真正出问题的是写侧（Windows 文本层多补了一个 `\r`）。
**这种事我不实测就说不准，所以要动手跑 2×2 组合矩阵，不能靠印象。**
