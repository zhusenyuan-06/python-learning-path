```

**它返回的是 `False`，也就是"这两个号码不相等"。**

> 这正是 **11-01 你 fail 的那同一处**。当时的记录原文：

**正确的 ③ 应该这么答：**
> 类型混用**不一定报错**，要看做的是哪个操作：
> - `+` 拼接、`sorted` 排序 → 需要同类型 → **报 TypeError**

   没有撞上的时候是静默错误不会报错，所以更难发现
```

**① 完全正确**，连"掩盖原始异常"都点到了。

**② 完全正确**，标准答案就是 `raise` 与 `if` 平级、在 except 块内：

        f.write(json.dumps(tasks, ensure_ascii=False))

except Exception:
    if TMP_FILE.exists():
        TMP_FILE.unlink()                # 崩了就清掉临时文件
    raise                                # ✅ 与 if 平级，在 except 块内
# 口诀：raise 前面那行缩进多少，raise 就是多少 —— 它属于当前所在的块
```

**③ 核心答对了**："语法层面不管有没有活动异常 → 语法全绿 → 运行时才炸"。

```

**`raise` 掉出 except 块后，只要执行到它，照样炸 RuntimeError** —— 哪怕 try 块根本没出错。
因为 `raise` 在那个位置已经不在任何 `except` 的上下文里了，它变成了一句"凭空重抛"。

> **记这一条：`raise` 只有在 except 块里才有意义。**
> 出了 except 块，它不是"安静地不做事"，而是"换个更费解的错误来炸你"（RuntimeError 取代了原本的 ValueError）。

### 第 7 题（E30）· ValueError vs TypeError 分不清

**判定：❌ fail —— ①② 全对，③ 答"不知道"**

你的作答：
```
① except TypeError: 这一行错误类型不对
② except ValueError:
③ 不知道，我又忘了为啥不是类型不对啊，'abc'是字符串和数字不是一个类型啊，
   为啥会抛值不对啊
```

**①② 完全正确。** ③ 的疑问也问得非常好 —— 这正是这道题的根。

**答案：你的推理里有一处关键误判 —— "'abc' 是字符串"恰恰说明"类型是对的"。**

`int()` 接受什么？官方接受 **str / bytes / 数字本身 / 浮点**。
所以 `"abc"` 是 `str`，**属于 int() 允许的类型** → 类型这一关是**通过**的。
问题出在**值**：`"abc"` 不是合法的数字表示 → **ValueError**。

实测对照：
```
int("abc")   -> ValueError: invalid literal for int() with base 10: 'abc'
int(None)    -> TypeError: int() argument must be a string, a bytes-like object or a real number, not 'NoneType'
int("")      -> ValueError: invalid literal for int() with base 10: ''
int([1])     -> TypeError: int() argument must be a string, a bytes-like object or a real number, not 'list'
int("12")    -> 成功，返回 12
```

> **口诀（错题池里登记的）：**
> **TypeError = 类型都不对**（`int(None)`、`int([1])` —— int() 压根不收这种类型）
> **ValueError = 类型对但值不合理**（`int("abc")`、`int("")` —— str 是对的，但内容不是数字）
>
> **判断顺序：先问"类型允许吗"→ 不允许是 TypeError；再问"值合法吗"→ 不合法是 ValueError。**

写 `except` 的时候也按这个顺序想：
`cmd[5:]` **永远是 str**，所以 `int(cmd[5:])` **只可能抛 ValueError，永远不可能抛 TypeError** ——
写 `except TypeError` 等于写了一句永远进不去的分支。

### 第 8 题（E31）· 写目标与读源用了同一个路径变量

**判定：✅ pass —— ①②③ 全对**

你的作答：
```
① with open(源, "w", ...) 这一行第一个路径应该是目标
② with open(目标, "w", encoding="utf-8", newline="") as f:
③ 当场就清空
```

**① 完全正确。** ② 与标准答案一致：
```python
源 = Path("..") / "projects" / "error-tracker" / "错题追踪.json"   # 只读
目标 = Path("输出") / "错题表.csv"                              # 只写
with open(源, "r", encoding="utf-8") as f:                    # 读用 "r"
    数据 = json.load(f)["items"]
with open(目标, "w", encoding="utf-8", newline="") as f:       # 写用 "w"，对象是目标

```

**③ "当场就清空" —— 答对了关键。** 实测证据：
```
open 之前  文件大小 = 18 字节，内容 = {"items": [1,2,3]}
open 之后  文件大小 = 0 字节   ← 已经清空了！
这时读回来 = ''   ← 旧数据已经不在磁盘上
```

注意：**只是 `open()`，一个字节都还没写**，文件就已经变成 0 字节了。

**为什么这比"覆盖"严重？**
- **覆盖** = 旧内容被新内容顶掉 → 至少新内容还在
- **清空** = 旧数据**当场从磁盘上消失** → 你后面写不写、写对写错，都已经晚了；
  中途崩溃 = 留下一个 0 字节文件，**数据没了**

**更稳的做法（你 11-04 学过的原子写入）：**
```python
with open(TMPF, "w", encoding="utf-8") as f:
    f.write(json.dumps(tasks, ensure_ascii=False))
os.replace(TMPF, DATA_FILE)
```
实测：`os.replace 之后 源文件内容 = {"items":[9,9,9]}`
—— 全程源文件要么是旧的完整内容，要么是新的完整内容，**永远不会出现 0 字节的中间态**。
