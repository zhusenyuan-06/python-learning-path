## T03 · 「网页打不开」不等于「git 推不上去」—— 两条通道要分开测

| 项 | 内容 |
|---|---|
| 踩过次数 | **4** |
| 标签 | 网络、排查、GitHub |
| 第一次 | 2026-10-27 |
| 最近一次 | 2026-10-28 |

**症状（当时看到什么）**

```text
浏览器打开 GitHub 经常崩，以为推不上；但实测 git ls-remote 却能成功。反过来也有：git 偶尔超时，浏览器却是好的。
```

**原因（为什么会这样）**

网页和 git 走不同的 CDN 边缘节点，成功率完全不一样。实测同一时段：网页 github.com/login 0-40%，git 的 info/refs?service= 6 个 IP 全部 10/10 = 100%。根因是校园网随机丢弃 TCP 443（ICMP 通但 TCP 握手超时），git 有重试所以稳得多。

**解法（怎么解决）**

- 两条通道分开测：网页用 github.com/login，git 用 <仓库>.git/info/refs?service=git-upload-pack
别用网页表现推断 git —— 测完再决定要不要改道
- 补充：push.sh 里做成 5 轮 × 6 IP 自动重试，通道不稳时能自动换 IP

**备注**：17:12 那次推送全挂，又想起这个坑 | 10-28 又掐一次：先测别的站点确认只有 GitHub 被掐，没在'再换个 IP'上白费时间 | 2026-10-28 又一次：浏览器能打开 github.com/login/device 完成授权，但 git 通道仍需 IP 池才能通 —— 网页通道与 git 通道确实分开

## T17 · GitHub 的 api.github.com 和 github.com 不在同一批边缘 IP —— 绑错会被 301 弹走

| 项 | 内容 |
|---|---|
| 踩过次数 | **2** |
| 标签 | 网络、GitHub、排查、API |
| 第一次 | 2026-10-28 |
| 最近一次 | 2026-10-28 |

**症状（当时看到什么）**

```text
curl https://api.github.com/user 返回 301，Location: https://github.com/user，响应体空，拿不到任何 API 数据；换 8 个 IP 全是 301
```

**原因（为什么会这样）**

GitHub 的 api 站点边缘节点在 .5/.6 段（140.82.112.5、140.82.112.6、140.82.113.5…），web 站点在 .3/.4 段（140.82.112.3、140.82.114.4…）。拿 web 的 IP 去解析 api.github.com，边缘节点会按 Host 把你路由到 github.com 站点 → 301

**解法（怎么解决）**

- api.github.com 要单独绑 .5/.6 段（实测 140.82.112.6 / 140.82.113.5 / 140.82.114.6 / 140.82.116.6 / 140.82.121.6 都返 200）；push.sh 原来的 LOCK_IP 把四个域名绑同一个 IP，属于绑错，但 push 本身不调 API 所以一直没暴露

**备注**：2026-10-28 晚首次撞上：查 token 身份时 API 一直 301

## T12 · GitHub 推送失败的四步诊断法 —— 别急着换 IP

| 项 | 内容 |
|---|---|
| 踩过次数 | **1** |
| 标签 | git、GitHub、网络、排查、DNS、代理 |
| 第一次 | 2026-10-28 |
| 最近一次 | 2026-10-28 |

**症状（当时看到什么）**

```text
git push 报 Recv failure: Connection was reset；push.sh 第 2 步 ls-remote 连不上就直接退出。反复换 IP 重试，40 分钟没进展。
```

**原因（为什么会这样）**

失败原因分四层：链路整体断 / DNS 被阻 / 代理没生效 / IP 池整段过期。不按顺序排查就瞎试 IP，等于在错误的层面上反复用力。

**解法（怎么解决）**

- ① 先测别的站点（百度/Gitee/GitCode/B站）：全部 200 → 网络正常，只有 GitHub 被掐，别去改路由器
- ② nslookup github.com：超时 → DNS 被阻。但 git 走锁定 IP 时不受影响，照样能 push
- ③ env | grep proxy：WorkBuddy 注入的 127.0.0.1:54880 只放行特定域名，对 GitHub 无效 —— 脚本里 unset 掉是对的
- ④ 扫 IP 池：原 6 个 IP 全部 TCP 握手失败（curl 返回 000）。GitHub 封 IP 是整段随机的 → 必须扩池（6→12），换顺序没用
- 关键：curl 探测 200 不等于 git push 成功（中间隔着 git 自己的 HTTP/2 + 认证层）→ 探测阶段和推送阶段必须各自独立重试
- 脚本改造：push.sh 第 2 步 ls-remote 失败不再 exit 1，改为提示后继续（推送阶段本来就有独立换 IP 重试）；第 5 步不再 2>/dev/null 吞报错，捕获到 LAST_ERR 再打印并给出分诊指引
- 2026-10-28 补充：curl 探测 200 只代表 GET 通，GitHub 的 POST 端点（/login/oauth/access_token）由不同边缘节点转发，必须按方法分开测（详见 T16）；另外 WorkBuddy 注入的代理端口每次会话都会变（54880 → 50011），所以别写死端口，一律 unset 掉

## T13 · git push --dry-run 给你「假绿」—— 本地==远端时根本不触发认证

| 项 | 内容 |
|---|---|
| 踩过次数 | **1** |
| 标签 | git、认证、排查、GitHub |
| 第一次 | 2026-10-28 |
| 最近一次 | 2026-10-28 |

**症状（当时看到什么）**

```text
删掉 GitHub Token 后，git push --dry-run origin main 依然 exit=0、零报错，误以为认证没问题；结果真推时立刻 fatal: unable to get password from user
```

**原因（为什么会这样）**

- 要测认证必须造一个真实写操作：git push origin main:refs/heads/_authtest_tmp 推临时分支，推得动说明认证通，再 git push origin --delete _authtest_tmp 清理

## T14 · WorkBuddy 注入的本地代理会让 GitHub 连不通 —— 直连 200、走代理 000

| 项 | 内容 |
|---|---|
| 踩过次数 | **1** |
| 标签 | 网络、代理、WorkBuddy、排查、GitHub |
| 第一次 | 2026-10-28 |
| 最近一次 | 2026-10-28 |

**症状（当时看到什么）**

```text
curl https://github.com 返回 http_code=000 且 remote_ip 为空，但同一时刻加 --noproxy "*" 就返回 200；push 也报 Failed to connect to github.com:443
```

**原因（为什么会这样）**

WorkBuddy 沙箱会注入 http_proxy=http://127.0.0.1:50011，这个本地代理对 GitHub 的 CDN 链路不通；DNS 超时和「连不上」常常是这个代理造出来的假象，不是真的没网

**解法（怎么解决）**

- 访问 GitHub 前先 unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY 并 export NO_PROXY="*"；curl 再额外加 --noproxy "*"；git 用 push.sh 开头那行同名 unset（原本就在）

## T15 · GCM 设备流在非交互 shell 里拿不到设备码 —— 改走手动 OAuth Device Flow

|---|---|
| 踩过次数 | **1** |
| 标签 | 认证、OAuth、WorkBuddy、排查、GitHub |
| 第一次 | 2026-10-28 |
| 最近一次 | 2026-10-28 |

**症状（当时看到什么）**

```text
git credential-manager github login --device 报 fatal: Cannot prompt because terminal prompts have been disabled；或者 exit=0 但屏幕上一个字都没有，像什么都没发生
```

**原因（为什么会这样）**

## T16 · GitHub 的 GET 通道通 ≠ POST 通道通 —— 换 IP 时要按方法分开测

| 项 | 内容 |
|---|---|
| 踩过次数 | **1** |
| 标签 | 网络、GitHub、排查、校园网 |
| 第一次 | 2026-10-28 |
| 最近一次 | 2026-10-28 |

**症状（当时看到什么）**

```text
同一批 IP 里 GET .../info/refs?service=git-upload-pack 全部返 200，但 POST /login/oauth/access_token 全部超时零响应，一个字都收不到
```

**原因（为什么会这样）**

GitHub 不同边缘节点对 GET 和 POST 的转发策略不一样；校园网链路抖动叠加后，就出现「读得回来、写不回去」的局面

**解法（怎么解决）**

- IP 池探测要按方法分开测；轮询换 token 用「多 IP × 多轮」轮换而不是死磕一个 IP；curl 加 -v 看清是「握手后无响应」还是「压根没连上」，两者解法不同

## T18 · git push 报「失败」但服务端其实已经推上去了 —— 别急着重推

| 项 | 内容 |
|---|---|
| 踩过次数 | **1** |
| 标签 | git、网络、GitHub、排查 |
| 第一次 | 2026-10-28 |
| 最近一次 | 2026-10-28 |

**症状（当时看到什么）**

```text
git push 报 fatal: Recv failure: Connection was reset，exit=128；紧接着换 IP 再推却输出 "Everything up-to-date"，exit=0 —— 第一次「失败」的那次其实已经成功了
```

**原因（为什么会这样）**

git 协议是「客户端推 pack → 服务端解包并更新 ref → 回传确认」。连接在最后一步断掉时，服务端 ref 已经更新了，客户端没收到 ack 就报失败。校园网链路抖动下这个现象极常见

**解法（怎么解决）**

- push 报网络类错误后，先查远端 HEAD 再决定要不要重推：git ls-remote origin refs/heads/main 比对本地 git rev-parse HEAD，一致就说明已成功。也可以用 API：GET /repos/<owner>/<repo>/commits/main（注意 api.github.com 要绑 .5/.6 段 IP）

## T19 · git config 里 curloptResolve 绑的 IP 也会整段过期 —— 不用改 hosts，改 git config 就能绕过管理员权限

| 项 | 内容 |
|---|---|
| 踩过次数 | **1** |
| 标签 | git、GitHub、网络、排查、IP池、hosts、curloptResolve |
| 第一次 | 2026-10-29 |
| 最近一次 | 2026-10-29 |

**症状（当时看到什么）**

```text
git push 报 fatal: unable to access 'https://github.com/...': Recv failure: Connection was reset
curl https://github.com 返回 000 且 remote_ip 为空
git config --global --get-regexp curloptResolve → 绑的是 140.82.121.3（昨天还好好的，今天已死）
hosts 里绑的 20.27.177.113 同样已死（curl --resolve 验证返回 000）
```

**原因（为什么会这样）**

GitHub 的边缘 IP 是分批下线的，某个 IP 今天通明天就可能 000。git 的 `http.https://域名/.curloptResolve` 会**优先用绑定的 IP**，绑的 IP 一死就完全绕不过去；hosts 的绑定同理。

T12 说的「IP 池整段过期」不只是 hosts —— **git config 里的绑定同样是定时炸弹**，而且它比 hosts 更隐蔽：hosts 挂了浏览器打不开，一眼能看见；git config 挂了你会以为是网络抽风。

另外还发现桌面《修复GitHub访问.bat》(v1) 把**同一个 IP 同时绑给 `github.com` 和 `api.github.com`**，违反 T17 —— 就算 hosts 修好了，API 调用仍然会 301。

**解法（怎么解决）**

- **不用改 hosts**：改 hosts 要管理员权限，WorkBuddy 沙箱直接被拒（T06）。改用 git config 的 **URL 级** `curloptResolve`，一个域名绑多个活 IP 做冗余，git 侧完全不需要提权
  ```bash
  git config --global --unset-all "http.https://github.com/.curloptResolve"
  git config --global --add "http.https://github.com/.curloptResolve" "github.com:443:140.82.112.3"
  # 一个域名可以 add 多个 IP，git 会依次尝试
  ```
  注意 T01：**不带 URL 前缀**的 `http.curloptResolve` 是单值键，多次设置会互相覆盖
- 探测可用 IP：`curl -s -o /dev/null -w '%{http_code}' --noproxy '*' --resolve "github.com:443:" https://github.com/login`，返回 **200** 才是活的
- **web 段和 api 段要分开**（T17）：web（github.com / codeload / objects）用 `.3/.4` 段；api.github.com 用 `.5/.6` 段。实测 2026-10-29 可用：
  - web：`140.82.112.3` / `140.82.114.3` / `140.82.116.3` / `140.82.112.4` / `140.82.114.4`
  - api：`140.82.112.6` / `140.82.113.5` / `140.82.114.6` / `140.82.116.6`
- api 的探测路径要用 `https://api.github.com/` 根路径（返 200），用 `/user` 会返 **401** —— 别把 401 当成不可用
- **curl 不读 git 的 config**：单独调 API 时必须自己加 `--resolve "api.github.com:443:<api段IP>"`，否则拿到的是 301 空响应
- hosts 层面仍需管理员：把《修复GitHub访问_v2.bat》交给用户双击（脚本自己 `Start-Process -Verb RunAs` 提权）。v2 相比 v1 修正了 T17：web 段和 api 段分开探测、分开写入
- **交付 .bat / .sh 前的自检流程**（这次踩到的）：转成 CRLF（bat）→ 拿 hosts **副本**实跑一遍 → 确认 exit code、改写结果、非 github 行零丢失，三样都对再让用户双击
- **管道会吃掉退出码**（今天又踩了一次）：`if git push ... | tail -3; then` 判断的是 `tail` 的成功与否，不是 git 的。必须重定向到临时文件再判断：`if git push ... > /tmp/x.log 2>&1; then`

## ⚠️ T19 二次修正（2026-10-29 19:05 实测推翻了我自己的第一版结论）

**第一版以为「池子铺满就能容错」—— 错了。**

给 github.com 配了 **20 条** IP，push 依然全败。开 `GIT_TRACE_CURL=1` 一看：

```text
Trying 140.82.121.4          ← 只试了这一个！就是配置里【最后加的那条】
Failed to connect to github.com:443 after 21074 ms
```

**修正一：git 的 `http.https://<域名>/.curloptResolve` 每个 URL 只认一个 IP。**
配 20 条进去，git 只用最后一条，**既不会「多值共存」，也不会按顺序逐个回退**。
（T01 说的「多值共存」是指 4 个**不同 URL** 各配一条，不是同一个 URL 配多条 —— 我自己读岔了。）

对照实验证明是 git 的锅，不是 curl 的锅 —— curl 明明会回退：

```text
只绑死的 .121.6          → 000
死的 .121.6 + 活的 .121.3 → 200 ✅   ← curl 会回退，git 不会
```

**修正二：可达的 IP 集合会随时段轮换，不是「某个 IP 死了」。**

| 时间 | 实测能通的 web 段 IP |
|---|---|
| 18:35 | .112.3 / .113.3 / .114.3 / .116.3 / .112.4 / .114.4（6 个） |
| 19:00 | 同一批全灭，只剩 **.121.3** |
| 19:05 | 又变成 **.112.3** + .113.5 |

**所以：任何写死的 IP 配置（包括 hosts、包括 git config）过一段时间就必然失效。**
唯一正确的做法是**每次推送前实时探活**：

```bash
# ① 探活：逐个试候选，取第一个返 200 的
# ② 绑单 IP：一个域名一条
# ③ 立刻 push
# ④ ls-remote 比对本地 HEAD 确认（T18）
```

**已把这套流程写进仓库里的 `push_github.sh`（v2，重写了旧版）** —— 旧版还在找已经删掉的 PAT 文件、还把 4 个域名绑同一个 IP（违反 T17）。以后直接跑它就行。

## T01 · git http.curloptResolve 是单值键，多次设置互相覆盖 —— 且同一个 URL 也只能留一个 IP

| 项 | 内容 |
|---|---|
| 踩过次数 | **1** |
| 标签 | git、配置 |
| 第一次 | 2026-10-27 |
| 最近一次 | 2026-10-27 |

**症状（当时看到什么）**

```text
给 4 个域名各设了一次 http.https://<域名>/.curloptResolve，结果 git config --get-regexp 查出来只剩最后一条。github.com 能连通，但 api/codeload/objects 全部失败。
```

**原因（为什么会这样）**

http.curloptResolve（不带 URL 前缀）是单值键，后设的直接覆盖前面的。必须用带 URL 前缀的 http.https://<域名>/.curloptResolve，那种是 URL 级配置，可多值共存。

## ⚠️ T21 三个「会骗你」的东西（2026-10-29 19:15~19:35 排障实测）

### 坑 A：bat 的 `echo` 会吃掉 `>` 后面的代码行

v2 修复工具用 `>> tmp echo <python代码>` 逐行拼一个临时 py 文件。跑出来：

```
File "C:\Users\15816\AppData\Local\Temp\gh_fix2.py", line 25
  nm = parts[1].lower()
IndentationError: unexpected indent
```

**不是缩进写错了。** 用 diag bat 实测复现（`笔记/_自检脚本/_诊断bat_echo缩进.py`）：

```
 24 | 期望 4 | 实际 4 |     parts = s.split()
 25 | 期望 4 | 实际 8 |         nm = parts[1].lower()   <<<< 不一致
```

第 25 行本该是 `if len(parts) >= 2:`，**它整个消失了**。

真相：**cmd.exe 的 `echo` 参数里 `>` 是重定向符**。
`echo     if len(parts) >= 2:` 被解析成「把 `= 2:` 当成输出文件名」，
这一行被重定向到了别处，临时 py 里就少了这么一行 → 后面的行整体上移 → 缩进错位。

> **结论：不要在 bat 里拼代码。**
> Python 独立成文件，bat 只负责「检查管理员 → 调 python → pause」。

### 坑 B：curl 的 `000` 不是状态码

自制的 probe() 判定写成：

```python
if len(code) == 3 and code.isdigit():      # ❌ "000" 也满足！
    return True
```

curl 连不上时 `-w "%{http_code}"` 输出的是 **`000`** —— 3 位数字、isdigit 为真，
于是「TCP 都没连上」被当成了「拿到了 HTTP 响应」。

```python
if len(code) == 3 and code.isdigit() and code != "000":   # ✅
```

而且判定标准要**按 host 分开**：
`github.com/login` 稳定 200；`api.github.com/` 根路径 301（跳主站）属正常；
`raw.githubusercontent.com/` 也是 301。一刀切要 200 会误杀。

### 坑 C：单次探测有一半是假的

```
raw.githubusercontent.com 连测 10 次：
301 000 301 000 301 000 301 301 000 000
成功率 5/10
```

校园网对 185.199.x 段有约 50% 丢包/限流，连接会在 0.09 秒被 RST。

> **探测必须重试。** 规则：**任一次成功就算活（宽松），全都失败才算死（严格）**。
> 这样「把活 IP 判死」和「把死 IP 判活」两个方向都能躲开。

### 附带发现：同一个 IP 对不同域名表现不同

今天实测 `20.27.177.113`：

- 探 `api.github.com`（第 4 步）→ 通了，判**活**

所以「验证现有绑定」和「新 IP 探测」必须**分别做**，不能共用一次结论。

## ⚠️ T22 探活必须并发（2026-10-29 20:26~20:31 实测）

### 窗口到底有多短：4 分钟翻了 4 次

```

20:27  push_github.sh v3 探 → web 活 5 个、api 活 2 个 → push 成功
```

### 串行 vs 并发：差 N 倍

```
串行：总耗时 = Σ 每个 IP 的耗时 = N × 重试数 × 超时
并发：总耗时 ≈ max(每个 IP 的耗时)      =       重试数 × 超时
```

v3 工具的候选池合计 50 个（web 26 + api 16 + raw 8）：

| | 最坏耗时 |
|---|---|
| 串行 | 50 × 3 × 6 = **900 秒（15 分钟）** |
| 并发 | 3 段 × 3 × 6 = **36 秒** |

窗口几十秒 → 串行工具不是「慢一点」，是**必然白跑**。

### 改造：pick_ip

```python
def pick_ip(ips, host, path="/", strict_200=False, workers=16, ...):
    def _one(ip):
        if strict_200:
            return ip, (probe(host, ip, path, timeout, tries) == "200")
        return ip, (probe(host, ip, path, timeout, tries) != "000")
    with concurrent.futures.ThreadPoolExecutor(max_workers=n) as ex:
        results = dict(ex.map(_one, ips))
    for ip in ips:            # 按候选顺序挑第一个活的 = 保住优先级
        if results.get(ip):
            return ip
    return None
```

改造后实测（hosts 副本全链路）：**51 秒跑完，校验全部通过**。

### 附带修正：用可复现输入做性能对比

我第一次测出来的结论是「串行 45 秒 vs 并发 51 秒」—— 差点写成「并发更慢」。
真相是两次运行之间 raw 段抖动方向相反，**跟算法没关系**。

正确做法：用 RFC 5737 保留测试段 `192.0.2.0/24`（全球不可达，行为 100% 确定）。

```
基准：探测 10 个必然不可达的 IP，单次超时 4s，重试 3 次
  串行版： 120.9 秒
  并发版：  12.1 秒
  倍数：串行是并发的 10.0 倍      ← 恰好 = IP 个数
```

> **真实网络只用来做功能验证，不用来做性能对比。**
> 要比性能，就得用行为确定的输入。

**一句话记住**：**窗口只有几十秒，串行扫描等于用过期信息做决策 —— 探活一律并发。**
