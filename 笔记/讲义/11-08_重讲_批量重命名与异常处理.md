# 一、批量重命名脚本

## 1. 重新定位：批量改名 = 没有事务的批量更新

**改 1 个文件 vs 改 50 个文件，差别在哪？**

- 改 1 个：`os.rename(a, b)`，一行，出错立刻看见，改错了手动改回来。
- 改 50 个：**50 个独立的失败点**，每一个都可能不可逆，而 Python 的文件系统
  **没有「全部撤销」这种原子操作**（数据库里叫 transaction，文件系统没有）。

所以这个脚本真正的难点从来不是 `rename()` 怎么调，而是：

> **你怎么在没有事务的前提下，自己造出事务来。**

造事务需要三样东西：

| 你需要的能力 | 手段 | 防的是什么 |
|---|---|---|
| 动手前先看清楚要干什么 | 干跑（dry-run） | 「盲改」—— 改完才发现改错了 |
| 动手前挡住必然出错的那些 | 冲突预检 | **静默覆盖** —— 文件内容直接没了 |
| 动手后还能退回去 | 操作日志 + 撤销 | 「不可逆」—— 没有退路 |

## 2. 四步流水线

**顺序不能换**，因为每一步的信任级别是递增的：前一步的结果是下一步的输入，
输入一旦错了，后面全是错的。

| 步骤 | 函数 | 动文件了吗 | 信任级别 |
|---|---|---|---|
| ① 收集计划 | `收集计划()` | ❌ 纯读 | 只是「打算」，可能全错 |
| ② 找冲突 | `找冲突()` | ❌ 纯读 | 已排除掉「必然会覆盖」的项 |
| ③ 打印计划表 | `main()` | ❌ 纯读 | **用户亲眼确认过** |
| ④ 执行 + 写日志 | `执行改名()` + `写日志()` | ✅ **只有这一步动** | 已授权 |

**一句话**：前三步都是「看」，只有第四步是「做」。

> ⚠️ 干跑模式下 **② 找冲突也要做**。
> 「不执行改名」不等于「不检查」—— 冲突检查是纯只读操作，
> 而这正是干跑的价值：让你在改之前就看到「有 3 个会冲突」。

## 3. 安全三件套

### ① 干跑默认开（dry-run）

不加 `--apply` 就只打印计划表，什么都不改。

**为什么默认必须是干跑**：批量改名是**不可逆操作**。
「危险的操作必须是需要显式申请的那一个」—— 这是命令行工具的通用原则。
如果默认就真改，用户手快敲错一个字符就全完了。

### ② 冲突预检

目标名已存在 → **跳过 + 报告，绝不覆盖**。

**为什么不能靠 `rename()` 自己报错？** 因为它跨平台不一致：

| 平台 | `Path.rename()` 目标已存在时的行为 |
|---|---|
| Windows | 抛 `FileExistsError`（拒绝覆盖）✅ |
| Linux | **静默覆盖**，原文件内容直接没了 ❌ |

同一个脚本在 Windows 上给你报错，在别人 Linux 上把文件吞了。
**所以必须自己先查 `新.exists()`**，让两个平台行为一致。

**具体场景**：你拍了个短剧，`第2集_草稿.mp4` 和导出的 `第2集_成片.mp4` 都在。
把 `草稿` 批量改成 `成片`：

- Windows：`FileExistsError`，草稿还在，成片也在 ✅
- Linux：**成片被草稿的内容覆盖了** —— 你辛苦导出的那版没了，而且**没有任何提示** ❌

### ③ 操作日志 + 撤销

每次真改名记一份「旧名 → 新名」，`--undo` 可以改回去。

**为什么必须有**：批量操作必须有退路。
且撤销要处理「撤销本身也可能失败」（原名被别人占了 / 文件被删了）。

## 4. 三个实测坑（换场景重讲）

### 坑 1：静默搬家 ——「改名」悄悄变成「搬家」

**场景**：统一归档课程资料，敲了

```bash
python batch_rename.py "D:/课程资料" "" "第3期/"
```

**实测结果**：

| 写法 | 结果 |
|---|---|
| `p.with_name(新文件名)` | `ValueError: Invalid name '第3期/a.txt'` —— 报错明确，但白搭 |
| `目录 / 新名字` | **如果 `第3期/` 这个目录恰好存在，文件被真的搬进去** |

改完之后：根目录空了，多出来一个 `第3期/` 文件夹。
**全程零报错、退出码 0、终端还打印「完成：成功 50 个」。**

这是最阴险的地方——你以为改的是**名字**，实际改的是**位置**。

**防线**（`batch_rename.py` 第 493 行）：

```python
if "/" in args.新片段 or "\\" in args.新片段:
    print("❌ 新片段不能包含路径分隔符 / 或 \\")
    return
```

**为什么 `with_name()` 是对的**：它只接受**纯文件名**，`"sub/a.txt"` 会被直接拒掉。
而 `目录 / 新名字` 是路径拼接——**它不区分「这是个名字」还是「这是个路径」**。

> **改名用 `with_name()`，移动用 `/`。混着用就会静默搬家。**

### 坑 2：文件被占用 —— 捕获粒度决定成败

**场景**：`报告_v1.txt` 用 VSCode 打开着，然后跑 `--apply`。

**实测报错**：`PermissionError: [WinError 32] 另一个程序正在使用此文件`

跟 todo-cli 里 `os.replace` 踩的是**同一个坑**（Windows 文件锁）。

**关键问题不是「怎么修」，是「修的粒度在哪」**：

| try 的位置 | 3 个文件中间 1 个被占用 | 结果 |
|---|---|---|
| 循环**外** | 改 1 个就中断 | 只改了 1 个，但**报告说「成功 1 个」** |
| 循环**内** | 跳过那一个，继续 | 改了 2 个，1 个报「被占用」—— **正确** |

所以代码里是**每个文件单独 try/except**（第 249-270 行）。

### 坑 3：静默漏改 —— 一半改了，一半没改

**场景**：100 个文件要改，却写成：

```python
for p in 目录.iterdir():      # ❌ 直接遍历生成器
    p.rename(p.with_name(新名))
```

**实测结论**：`iterdir()` 和 `glob()` 返回的都是**生成器**，不是列表。
一边迭代一边改名，目录内容在变，迭代器可能跳过元素。

结果：改了 88 个，剩 12 个还是旧名。**不报错、退出码 0、打印「成功 88 个」。**

比坑 1、坑 2 都危险——坑 1、坑 2 打开目录一眼就看见了，
而**漏改的文件名看起来完全正常**。

**修法**（第 154 行）：

```python
for p in list(目录.iterdir()):   # ✅ 先 list() 冻成实体列表
```

`list()` 的作用：**把「边走边看」变成「先拍一张快照，再照着快照做事」**。

## 5. 代码里的 5 个 Python 细节

| # | 细节 | 一句话原理 | 写错的后果 |
|---|---|---|---|
| ① | `with_name()` 只换文件名 | 它**只接受纯文件名**，给路径就报错 | 用 `/` 拼 → 静默搬家 |
| ② | `and` 的短路特性 | `p.suffix` **永远是字符串**，`p.suffix != None` 恒为 True | 少了前半句 → 所有文件被过滤 → **静默错误** |
| ③ | `except` 从具体到宽泛 | 按顺序匹配，**命中第一个就停** | `except OSError` 写前面 → 下面分支**永远走不到** |
| ④ | 捕获放在「能做出决策」的那层 | 决策粒度 = 恢复粒度 | 循环外捕获 → 改 1 个就停 |
| ⑤ | 日志用 `\t` 不用空格 | 路径里**可能有空格** | `split(" ")` 把一个路径拆两半 → 撤销全崩 |

第 ② 条展开：

```python
if p.suffix != None:                              # ❌ 恒为 True，所有文件都不匹配
if 扩展名 is not None and p.suffix != 扩展名:      # ✅ 短路：左边假了右边不求值
```

写错时脚本输出「**没有需要改的文件**」——一本正经地告诉你结果，
其实它是"我什么都没干"。这跟错题本里 **E15 静默错误** 是同一族。

## 6. 撤销的方向是反的

日志记 `旧名 → 新名`，撤销就**倒着走**：

```python
# 写日志
成功.append((旧, 新))        # 旧 → 新
f.write(f"{旧}\t{新}\n")

# 撤销
新.rename(旧)                  # ← 反过来
成功.append((新, 旧))
```

写反了会「撤销成改名」：本来想把 `报告_v2.txt` 改回 `报告_v1.txt`，
结果它把 `报告_v1.txt` 改成了 `报告_v2.txt`——**越撤越乱，且每撤一次错得更离谱**。

# 二、异常处理最佳实践

## 1. 异常层级

```
BaseException
├── Exception                    ← 常规可捕获的都在这
│   ├── OSError
│   │   ├── FileExistsError
│   │   ├── PermissionError
│   │   └── FileNotFoundError
│   ├── ValueError
│   └── TypeError
├── KeyboardInterrupt            ← 不该捕获（Ctrl+C）
└── SystemExit                   ← 不该捕获（sys.exit()）
```

**本机实测**：

```
issubclass(KeyboardInterrupt, Exception) = False
issubclass(SystemExit, Exception)      = False
```

→ 写 `except Exception` **不会**误伤 Ctrl+C 和 `sys.exit()`。

## 2. 四条原则

### 原则 ①：不要裸 `except:`

**反例**：

```python
def 转数字(s):
    try:
        return int(s)
    except:          # ❌
        return -1
```

**实测**：`转数字("abc")` → `-1`，**调用方完全不知道出错了**。

这就是错题本里 **E15 静默错误** 的典型：程序不崩、结果是个"看起来合理"的值。
调用方拿到 `-1` 会当成「这是个负数」，然后拿它去算账。

裸 `except:` 会把**所有**异常都吃掉，包括 `ValueError`、`KeyboardInterrupt`、`SystemExit`。

**该写什么**：

```python
except ValueError as e:      # 只接我预期的那个
    记下来(f"非法数字: {s}")
    return None
```

### 原则 ②：捕获要放在「能做出正确决策」的那一层

| 捕获位置 | 3 个文件里 1 个失败 | 谁做决策 |
|---|---|---|
| 循环外 | 改 1 个就停 | 调用方不知道该重试哪个 ❌ |
| 循环内 | 跳过 1 个，改 2 个 | 这一层知道「哪个失败了、为什么」✅ |

**判断标准**：这一层有没有**足够的信息**做出决定？

- `执行改名()` 知道「是哪个文件、报什么错」→ 能决定「跳过它，继续下一个」✅
- `main()` 只知道「批量改名失败了」→ 做不出「哪个该重试」的决定 ❌

### 原则 ③：`try` 的范围要小

**反例**：

```python
try:                              # ❌ try 包住了整个循环
    for 旧, 新 in 计划:
        旧.rename(新)
        写日志(...)
except PermissionError:
    print("有文件被占用")
```

如果抛的是 `FileNotFoundError`，它**不会**被 `except PermissionError` 接住 → 直接崩。
但如果图省事写 `except OSError`，那「磁盘满」「路径太长」「文件被占用」「源文件不存在」
**全被压成同一句话**，用户完全无法判断该干什么。

**正确**：try 只包住**可能抛出你想抓的那个异常**的那几行。

### 原则 ④：捕获后必须处理或重抛，不能吞

判断标准：**捕获之后，你的代码有没有做出一个「这个错误被妥善处理了」的决定？**

| 姿势 | 代码 | 什么时候用 |
|---|---|---|
| ① 记下来 + 继续 | `失败.append((旧, 原因))` | 批量处理，一个失败不影响其他的 |
| ② 原样重抛 | `raise` | 我接不住，但上层能处理 |
| ③ 包装后重抛 | `raise XxxError(...) from e` | 我知道这是我的问题，但要加上下文 |

第 ③ 种的 `from e` 别省——它保留因果链：

```python
raise ValueError("参数不合法")          # ❌ 原始 TypeError 消失了
raise ValueError("参数不合法") from e   # ✅ 链式追踪
```

> **不捕获 = 大声失败（loudly fail）；吞掉 = 安静地失败（silently fail）。永远选前者。**

# 三、作业答案（本机实测）

## 问题 1：`Path.rename()` 在源文件不存在时抛什么？

**答案：`FileNotFoundError`**（`[WinError 2] 系统找不到指定的文件。`）

```
MRO: FileNotFoundError → OSError → Exception → BaseException
```

- 是 `OSError` 的子类 → 现在的代码**不会崩**，会被 `except OSError` 接住
- 但提示**误导**：

```
⚠️ 报告_v2.txt：系统错误：[WinError 2] 系统找不到指定的文件。
```

用户看到「系统错误」会以为是磁盘/权限问题，真实原因只是「这个文件已经不在那了」。

**结论：值得单独加一条**，放在 `except OSError` **之前**：

```python
except FileNotFoundError:
    失败.append((旧, "源文件不存在（可能已被移动或删除），已跳过"))
```

## 问题 2：`--undo` 那条路（`读日志撤销`）有同样的问题吗？

**有，而且更严重。实测三种情况。**

### 情况 A：改名后手动删了其中一个文件，再撤销

```
撤销完成：✅ 成功 1 个，❌ 失败 1 个
  ⚠️ 报告_v2.txt：系统错误：[WinError 2] 系统找不到指定的文件。
```

→ 同样缺 `FileNotFoundError` 分支。**这是上面那条修复的主要受益场景**，
因为撤销时源文件真的非常容易不见（你改名后又手动整理过）。

### 情况 B：撤销成功之后，再撤销一次

```
撤销完成：✅ 成功 0 个，❌ 失败 2 个
  ⚠️ 报告_final_v2.txt：系统错误：[WinError 2] ...
  ⚠️ 报告_v2.txt：系统错误：[WinError 2] ...
```

**根因**：`读日志撤销` **只读日志，从不更新日志**。第一次撤销成功后，
日志里那几条记录原封不动还在，而对应文件已经改回旧名了。
第二次撤销再 `新.rename(旧)`，源文件（`新`）早就没了 → FileNotFoundError。

**暴露的设计缺陷：撤销不是幂等的，也没有「撤销后重写日志」。**

### 情况 C：一行日志解析失败 = 整个撤销中断

```python
旧, 新 = 行.split("\t")    # ⚠️ 这行在 try 外面！
```

拆不出正好 2 份时抛 `ValueError: too many values to unpack (expected 2)`。
**这行在 try 块外面** → 异常直接冒泡 → **整个 `--undo` 中断，后面所有文件都撤不了**。

> 本机实测：Windows 上文件名**不能**含 tab（`Errno 22`），所以本机不会自然触发；
> 但 Linux 上 tab 是合法文件名字符，日志被手工改坏同样会触发。

**这是「原则 ②」的反面教材**：解析失败是一个**可以处理的单行问题**
（跳过这一行、报告一下），却因为 try 位置放错，变成了**终止一切的致命错误**。

## 建议的修复清单（尚未动手，等你决定）

| # | 位置 | 改动 | 为什么 |
|---|---|---|---|
| 1 | `执行改名` 第 258 行前 | 加 `except FileNotFoundError` | 给出「源文件不存在」而非「系统错误」 |
| 2 | `读日志撤销` 第 336 行前 | 同上 | 这是最常触发的场景 |
| 3 | `读日志撤销` 第 322 行 | `split` 挪进 try，或改成 `行.rsplit("\t", 1)` | 一行坏掉不该让整个撤销崩 |
| 4 | `读日志撤销` 结尾 | 撤销成功后**重写日志**，只留失败的项 | 让撤销幂等 |
| 5 | `写日志` | 改成写 JSON（`json.dump`） | 彻底告别分隔符问题 |

## 附：这次重讲的核心一句话

> **批量改名最大的敌人不是崩溃，是「跑完了、显示成功了、其实结果不对」。**
>
> 干跑、冲突预检、日志、逐个 try/except —— 这四样本质上都在做同一件事：
> **让失败大声发生，而不是安静地消失。**
