## 二、【E24】`open(path, 'w')` 是「开门」，不是「存东西」

### 2.1 一句话结论

> **`open(path, 'w')` 一执行，文件立刻变成 0 字节。**
> 「写内容」是后面的另一件事。
> 崩在两者之间 → **文件还在，但内容没了**。

### 2.2 今天真跑的三个场景（不是伪代码，是实跑输出）

跑的是 `笔记/_自检脚本/_演示_open_w清空.py`，输出原文：

```
==================================================================
  0 字节文件是怎么来的 —— 三个场景真跑一遍
==================================================================

场景 A：先 open(...,'w')，再准备内容（你昨晚的写法）
    崩溃前        22 bytes  内容='[{"任务": "买菜"}]'
    ↓ 现在执行有 bug 的代码：tasks 还没定义就 f.write(tasks)
    💥 崩溃：name 'tasks' is not defined
    崩溃后         0 bytes  内容=''
    ⚠️ 文件内容没了 —— 这就是 0 字节的现场

场景 B：先把内容算好，再 open(...,'w')
    崩溃前        22 bytes  内容='[{"任务": "买菜"}]'
    ↓ 执行改好的代码：tasks 还是没定义
    💥 崩溃：name 'tasks' is not defined
    崩溃后        22 bytes  内容='[{"任务": "买菜"}]'
    ✅ 旧数据完好 —— 因为崩在 open 之前，文件根本没被开过

场景 C：写临时文件，成功后再 os.replace 覆盖（工程标准做法）
    崩溃前        22 bytes  内容='[{"任务": "买菜"}]'
    ↓ 执行：写临时文件时崩溃
    💥 崩溃：name 'tasks' is not defined
    崩溃后        22 bytes  内容='[{"任务": "买菜"}]'
    ✅ 旧数据完好 —— 临时文件被丢弃，原文件一个字节都没动
    💡 这是数据库、配置中心、git 都在用的「原子替换」模式

==================================================================
  三个场景，同一个崩溃点，结果完全不同：
==================================================================
    A  先开文件再算内容  →  💥 原文件被清空 → 0 字节
    B  先算内容再开文件  →  ✅ 崩在 open 之前 → 原文件完好
    C  写临时文件再替换  →  ✅ 崩在 replace 之前 → 原文件完好

  记住这句话：**open('w') 是「开门」的动作，不是「存东西」的动作。**
            崩溃发生在「开门之后、存进去之前」，数据就没了。
            所以正解永远是：先把要存的东西准备好，再开门。
```

> 💡 **看这三个场景的关键**：三段的**崩溃点完全相同**（都是 `tasks` 未定义），
> **崩溃信息完全相同**（都是 `name 'tasks' is not defined`），
> **唯独结果不同**（0 字节 vs 22 字节 vs 22 字节）。
> 唯一变量是**顺序**。

### 2.3 昨天你为什么答错

你的作答是：

```python
① with open(DATA_FILE, 'w', encoding='utf-8') as f 这一行的 '' 里面应该是 r
② with open(DATA_FILE, 'r', encoding='utf-8') as f
③ w 改为了 r，防止清空
```

你的推理链是：**「用了 w → w 会清空 → 所以该改成 r」**。

**问题在于**：这行代码的下一行是 `f.write(json.dumps(tasks))` —— 它本来就是「写」啊。
改成 `'r'` 之后，`f.write(...)` 会直接炸：

```
io.UnsupportedOperation: not writable
```

你把两个**不同层面**的问题混成了一个：

| | 是什么 | 出错层面 |
|---|---|---|
| **模式选错** | 这段代码本来要读，你写了 `'w'` | 逻辑意图层面 |
| **时机错了** | 这段代码本来要写，但**内容还没准备好，文件已经被清空了** | 执行顺序层面 |

E24 考的是**后者**。原代码的意图完全正确（就是要存 tasks），
错的是**执行顺序**：清空发生在「内容准备好」之前。

> 📌 **顺序：先问「本意是读还是写」选模式，再问「内容备好了吗」定时机。**

### 2.4 三种正解（按稳度排序）

**写法 A：先备好内容，再开文件**（最简单，能解决 90% 的场景）

```python
内容 = json.dumps(tasks, ensure_ascii=False)      # ① 先算好，这里不会崩
with open(DATA_FILE, "w", encoding="utf-8") as f:  # ② 再开文件
    f.write(内容)                                    # ③ 最后写
```

如果 `tasks` 未定义，崩在第 ① 步，**文件根本没被碰过**。

**写法 B：直接改顺序的最小改法**（和 A 等价，只是把「算」和「开」分开写）

```python
with open(DATA_FILE, "w", encoding="utf-8") as f:
    f.write(json.dumps(tasks, ensure_ascii=False))
```
→ 这是你现在的 `todo_cli.py` 第 51-52 行的写法。
**注意：它其实已经是「开门后才算」的顺序**（`json.dumps` 在 `with` 里面），
只是因为 `tasks` 总是有值，所以一直没炸。**别以为现在没事就永远没事**。

**写法 C：写临时文件 + `os.replace` 原子替换**（工程标准做法，今天练习 1 用这个）

```python
import os

def save_tasks(tasks, path=DATA_FILE):
    tmp = path + ".tmp"                            # ① 临时文件，和正式文件同目录
    try:
        with open(tmp, "w", encoding="utf-8") as f:
            f.write(json.dumps(tasks, ensure_ascii=False))   # ② 只写临时文件
        os.replace(tmp, path)                      # ③ 写成功了才替换正式文件
    except Exception:
        if os.path.exists(tmp):
            os.remove(tmp)                         # ④ 崩了就删掉临时文件，别留垃圾
        raise
```

`os.replace` 在同一文件系统上是**原子操作**：
不存在「复制到一半」的中间状态，要么全成功，要么全没发生。
数据库、配置中心、git 都在用这个模式。

> ⚠️ **临时文件必须在同一个目录**（不能放 `%TEMP%`），
> 否则跨文件系统 `os.replace` 会失败。

### 2.5 ③ 「原来为什么没报错？」的完整答案

> 原来为什么没报错？因为 `open(..., 'w')` 的「清空」**不是一条会报错的语句**，
> 它是打开文件时**顺带完成**的动作。程序不知道你接下来会不会写成功 ——
> 它先把文件清空，然后你崩了，于是留下一个 0 字节的空壳。
>
> **这就是「静默失败」最阴险的地方：出错的不是「清空」，是「没写进去」，
> 而「没写进去」不产生任何错误信息。**
>
> 10-28 17:29 你亲眼见过这个现场：`教学/todos.json` 变成 0 字节。
> **0 字节 = 清空成功 + 写入失败**，这是这个 bug 的精确指纹。

> 📌 **顺便把你自己的话还给你**（你写进 README 的）：
> 「现在我每次写 open 都会先想一遍：w 是我来定内容，r 是我只看不动。」
> —— 这句话**完全正确**，但昨天你在**读**这个知识点时用反了。
>
> **知识点的方向，和使用知识点的方向，是两回事。**

## 三、【E27】复制粘贴病：同一段代码出现第二次就该抽成函数

### 3.1 一句话结论

> **同一个 `with open(...)` 写文件的代码，在一个文件里出现第二次，就该抽成函数。**

### 3.2 危害有两个（你昨天答的是空的，今天必须答全）

**危害 1：改错地方。**
昨天 10-29 17:33 的真实现场（`projects/todo-cli/README.md` 第 196 行有记录）：

> 修缩进的时候，我要删的是 `quit` 分支里重复的 `with open(...)`，
> 结果手滑把 `add` 分支里的 `add_task(tasks, text)` 删了。
> 于是任务根本加不进去，验收第 1 条直接挂。

**为什么手滑？** 因为这两段代码**长得太像**：

```python
elif cmd == "quit":
    with open(DATA_FILE, "w", encoding="utf-8") as f:     # ← 第 1 份
        f.write(json.dumps(tasks, ensure_ascii=False))
...
elif cmd.startswith("add "):
    with open(DATA_FILE, "w", encoding="utf-8") as f:     # ← 第 2 份，长得几乎一样
        f.write(json.dumps(tasks, ensure_ascii=False))
```

**危害 2：漏改一处。**
这一份更阴险 —— 它**不报错**。
你改了 A 处，忘了 B 处，两份代码的行为悄悄变得不一样，
bug 极难查（因为从外面看「代码是通的」）。

### 3.3 正确写法：只写一份，其它地方调用它

```python
# ❌ 原来：同一段写文件的代码在文件里出现了 3 次
elif cmd == "quit":
    with open(DATA_FILE, "w", encoding="utf-8") as f:
        f.write(json.dumps(tasks, ensure_ascii=False))
...
elif cmd.startswith("add "):
    with open(DATA_FILE, "w", encoding="utf-8") as f:
        f.write(json.dumps(tasks, ensure_ascii=False))

# ✅ 正确：只写一份，其余地方调用它
elif cmd == "quit":
    save_tasks(tasks)
...
elif cmd.startswith("add "):
    add_task(tasks, text)
    save_tasks(tasks)
```

**③ 完整答案（昨天你空着的那段）：**

> 同一段逻辑只写一份，其它地方调用同一个函数。
> 因为复制粘贴的代码块**长得太像**，改的时候容易改错地方 ——
> 昨晚我就在 quit 分支和 add 分支之间删错了行，
> 把 add 分支的 `add_task(tasks, text)` 误删了，结果任务加不进去。
>
> 而且复制粘贴还有第二个隐患：**改了一处，忘了另一处**，
> 两份代码的行为悄悄变得不一样，bug 极难查。

### 3.4 E02 / E03 / E27 是同一个根因

这三道题看起来不同，其实是一件事：

| 题号 | 表面现象 | 根因 |
|---|---|---|
| **E02** | `sum_list(nums)` 里 `nums = 0` 把入参覆盖了 | **同一个变量名承担两种角色** |
| **E03** | 词频统计漏了 `.strip()`，标点污染结果 | **同一段清洗逻辑复制了多份，改一处漏一处** |
| **E27** | 写文件的代码复制了 3 份，改错地方 | **同一段逻辑复制了多份** |

> 📌 **一句话串起来：**
> **「重复」是所有这些 bug 的共同土壤。**
> 变量重复 → 角色混淆；逻辑重复 → 改一处漏一处。
>
> E02 的解法是「一个变量只干一件事」，
> E27 的解法是「一段逻辑只写一份」——
> **它们是同一条原则的两个方向。**

### 3.5 判断标准（很好用，两条）

> 📌 **规则 1（代码层面）：** 同一个 `with open(...)` 在一个文件里出现第二次，就该抽成函数。
> 这条规则能挡掉你昨晚 7 个 bug 里的 2 个。
>
> 📌 **规则 2（决策层面）：改动有没有清单。**
> 如果这次改动**没有一张「哪几处要改」的清单**，
> 说明你正在靠眼睛找 —— 而复制粘贴的代码**靠眼睛找必错**。
> 有清单 = 逐条打勾 = 不会漏。
> 没清单 = 靠记忆 = 迟早漏。

**怎么在实践中用规则 2：**
改代码前先写三行：

```
这次要改的：save_tasks 的写入逻辑
要改的地方：① save_tasks 函数 ② 旧版函数 ③ 讲义里的示例
```

然后**逐条打勾**。这不是形式主义 —— 它是**把「靠眼睛」换成「靠清单」**。

### 练习 1：写 `save_tasks(tasks)`，要求任何一步崩溃都不破坏已有的 `todos.json`

**要求：**
- 用**写法 C**（`os.replace` 原子替换）
- 崩在**任何一步**（`json.dumps` 崩、写临时文件崩、`os.replace` 崩），
  **已有的 `todos.json` 必须完好**
- 崩溃时**不留垃圾**（不留下 `.tmp` 文件）
- 函数要能指定存到哪个路径（方便测试时用临时文件）

**提示：**
- `import os`
- `tmp = path + ".tmp"`
- `os.replace(tmp, path)`
- `except` 里记得 `os.remove(tmp)`，然后**要把异常继续抛出去**（`raise`），
  不然调用方以为存成功了

**验收（自己跑一遍）：**
```python
# 造一个有内容的 todos.json
# 调用 save_tasks(某个会崩的数据)  ← 让它崩
# 检查：原文件内容还在吗？同目录下有 .tmp 残留吗？
```

### 练习 2：指出并改写 `add_task` / `mark_done` 里重复的写文件代码，抽成一个函数

**背景：** 练习文件里给了你一份**故意写成「复制粘贴版」**的代码，
`add_task` 和 `mark_done` 各自都写了一遍写文件的代码。

**要求：**
1. **指出**重复的写文件代码在**哪几行**（写行号）
2. **抽**成一个函数（名字自己起，建议 `save_tasks`）
3. **改写** `add_task` / `mark_done`，让它们**调用**这个函数
4. 改完之后，**原来那几份重复的代码全部删掉**（不是留着不用，是删掉）

**验收：**
- 全文 `grep 'with open'` 应该**只剩 1 处**（在抽出来的那个函数里）
