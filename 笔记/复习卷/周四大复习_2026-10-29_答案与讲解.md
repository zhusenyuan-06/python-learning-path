### 第 5 题（E24）· `open(path, 'w')` 会先清空再写

**判定：❌ fail —— 今晚唯一的方向性误解（但值得花时间搞懂）**

你的作答：
```
① with open(DATA_FILE, 'w', encoding='utf-8') as f 这一行的 '' 里面应该是 r，
   w 是写模式，会先清空
② with open(DATA_FILE, 'r', encoding='utf-8') as f
③ w 改为了 r，防止清空
```

你的推理链是：**「这行用了 w，w 会清空 → 所以应该改成 r」**。

**问题在于：这行代码的下一行是 `f.write(json.dumps(tasks))` —— 它本来就是「写」啊。**
改成 `'r'` 之后，`f.write(...)` 会直接报错：
```
io.UnsupportedOperation: not writable
```

**你把「模式选错了」和「时机错了」搞混了。** 这是两个完全不同层面的问题：

| | 是什么 | 什么时候出 |
|---|---|---|
| **模式选错** | 这段代码本来要读，你写了 `'w'` | 逻辑意图层面 |
| **时机错了** | 这段代码本来要写，但**写的内容还没准备好**，文件已经被清空了 | 执行顺序层面 |

这道题考的是**后者**。原代码的意图完全正确（就是要把 tasks 存进文件），
错的是**执行顺序**：清空发生在「内容准备好」之前。

**正确写法有两种：**

**写法 A：先备好内容，再开文件**（最简单）
```python
内容 = json.dumps(tasks, ensure_ascii=False)   # ① 先算好，这里不会崩
with open(DATA_FILE, 'w', encoding='utf-8') as f:   # ② 再开文件
    f.write(内容)                                     # ③ 最后写
```
如果 `tasks` 未定义，崩在第 ① 步，**文件根本没被碰过**。

**写法 B：原子替换**（更稳，工程上常用）
```python
import os
tmp = DATA_FILE + ".tmp"
with open(tmp, 'w', encoding='utf-8') as f:
    f.write(json.dumps(tasks, ensure_ascii=False))
os.replace(tmp, DATA_FILE)     # 写成功了才替换，失败原文件还在
```

**③ 正确答案应该是：**

> 原来为什么没报错？因为 `open(..., 'w')` 的「清空」不是一条会报错的语句，
> 它是打开文件时**顺带完成**的动作。程序不知道你接下来会不会写成功 ——
> 它先把文件清空，然后你崩了，于是留下一个 0 字节的空壳。
>
> **这就是「静默失败」最阴险的地方：出错的不是「清空」，是「没写进去」，
> 而「没写进去」不产生任何错误信息。**
>
> 昨晚 17:29 你亲眼见过这个现场：`教学/todos.json` 变成 0 字节。
> **0 字节 = 清空成功 + 写入失败**，这是这个 bug 的精确指纹。

> 📌 **顺便把你自己的话还给你**（你昨天写进 README 的）：
> 「现在我每次写 open 都会先想一遍：w 是我来定内容，r 是我只看不动。」
> —— 这句话**完全正确**，但今天你在**读**这个知识点时用反了。
>
> **知识点的方向，和使用知识点的方向，是两回事。**
> 「w 会清空」这个知识点没错；错的是你以为「这里不该用 w」。
> **先问「这段代码本意是读还是写」，再选模式。**

### 第 6 题（E25）· `not in` 和 `not` 混淆

**判定：❌ fail —— 未作答**

**正确写法：**
```python
if not path.exists(DATA_FILE):     # ✅
    tasks = []
```

**错在哪：**
```python
if path.exists(DATA_FILE) not in tasks:   # ❌
```

- `not in` 是**成员判断**：「x 在不在容器里」，右边**必须**是容器
  （list / dict / set / str / tuple）
- `not` 是**布尔取反**：「把 True/False 反过来」，右边是单个布尔值
- `path.exists(...)` 返回的是 `True`/`False`，**不是容器**
  → 拿布尔值去 `not in` 一个列表，语义上说不通

Python 不会立刻报错（`True not in []` 语法上合法，就是永远为 True），
所以它是**静默错误**：条件永远成立/永远不成立，你很难察觉。

> 📌 **这题你今天亲手犯过**（就在 `todo_cli.py` 的 `load_tasks` 里）。
> 写完那行你改对了，但**没记住为什么**。
>
> **记住这句话就够用**：
> `not in` 右边要能「装东西」，`not` 右边只能是一个开关。

### 第 9 题（E28）· 缩进栈层级不匹配

**判定：❌ fail —— 方向对，但没治本**

你的作答：
```
① 缩进多了
② 缩进改为12格
③ （空）
```

**① 说对了核心**（多缩进了）。

**② 「改为 12 格」不解决问题。** 12 格是「和 `add_task` 那行对齐」——
但**对齐不是 Python 关心的，层级才是**。

Python 的缩进是**栈**，不是「对齐美观」：

```
if cmd.startswith('add '):     ← 层级 1（缩进 4）
    if len(cmd) > 4:           ← 层级 2（缩进 8）
        """                    ← 层级 3（缩进 12）
        这里缩进 16 格了          ← 层级 4（缩进 16）← 栈里突然多了一层
        """                    ← 层级 3（缩进 12）  ← 回到 12？栈里有 12
    add_task(tasks, text)       ← 层级 2（缩进 8 或 12）
```

**报错不是因为「多了几格」，是因为「栈里没有这一层」。**
所以改格数是治标。

**真正的解法：这行 docstring 根本不该在这里。**

```python
if cmd.startswith('add '):
    text = cmd[4:]
    add_task(tasks, text)
```

docstring（`"""..."""`）是**函数的说明书**，应该写在 `def` 下面，
写在 `if` 分支里，它只是一个**没人用的字符串字面量** —— 白占地方，还会惹麻烦。

> 📌 **记住这两条：**
> 1. **缩进是层级栈，不是排版对齐。** 同一层必须缩进**完全一样**（4 格就 4 格，8 格就 8 格）。
> 2. **别把 docstring 放进 `if` 分支。** 它不执行任何功能，只会制造层级噪音。

**③ 完整答案：**

> 原来为什么报错？因为 docstring 那几行多缩进了一层，
> Python 建立缩进栈时遇到了一个「没进过也没退过」的层级，
> 下一行回到一个栈里不存在的缩进 → `IndentationError`。
>

### 2. 「错的东西有时比对的更安全」

### 3. E24 的教训：区分「模式选错」和「时机错了」

- 模式选错 = 这段代码要读，你写了 `'w'`
- 时机错了 = 这段代码要写，但**内容还没准备好，文件已经被清空了**

昨晚 0 字节的 `todos.json` 是**时机问题**，不是模式问题。
**先问「本意是读还是写」选模式，再问「内容备好了吗」定时机。**
