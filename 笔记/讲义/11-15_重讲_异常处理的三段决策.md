## 问题 ①：`except OSError: pass` —— 吞掉异常，还写着"交给报告"

### 代码现状

```python
# L650-656
for 临时, 最终 in reversed(已完成):
    try:
        if 最终.exists():
            最终.rename(临时)
    except OSError:
        pass                      # 撤不回来也只能算了，交给报告
```

### 问题在哪

注释最后一句写着「**交给报告**」。但你去看报告是怎么生成的——

```python
失败 = []
成功 = []
...
return 成功, 失败, 全局停止
```

`回滚临时名()` 的函数签名是：

```python
def 回滚临时名(临时映射, 已完成):
```

**它没有返回值。** 里面 `pass` 掉的异常，没有进 `失败` 列表，没有 print，
没有写日志，**没有任何一条路径能让调用方知道"回滚失败了"**。

注释说「交给报告」，但代码里**根本没有交给报告的那一步**。
注释描述的是一个不存在的行为——这是最危险的一类 bug：
**读代码的人（包括你自己三个月后）会以为这里有兜底。**

### 实测（本机跑出来的）

```
###### 测试4：回滚临时名 —— 撤不回来时会怎样？ ######
调用 回滚临时名（回滚必然失败）...
函数返回了 —— 没有抛异常，也没打印任何东西
结果：__tmp_xxx.txt 还在原地吗？ True

→ ✗ 没抛异常   ✗ 没打印   ✗ 没记入失败列表
  → 异常被【吞掉】了，调用方完全不知道回滚失败了
```

### 这为什么是最严重的一类错误

回到你错题本上的 **E15「静默错误三件套」**——它的定义是：

> 能跑，但结果是错的（缺 strip / 缺 reverse / 缺 else）

`except OSError: pass` 是 E15 的**加强版**。E15 至少还会在数据上留下痕迹（词频被污染、排名是反的），
**至少你事后还能看出来不对劲**。

而 `pass` 掉回滚异常的后果是：

- 文件停在 `__tmp_xxxx.jpg` 这种临时名上
- 终端输出「✅ 成功 0 个，❌ 失败 N 个」——**看起来像是一次正常的失败**
- 用户以为"哦这批没改成"，**实际上有一半文件已经被改了名、且再也回不去**

### 正确写法（三种，挑一种）

```python
# 方案A：让函数返回"撤不回来的清单"，由调用方合并进失败列表
def 回滚临时名(临时映射, 已完成):
    撤不回来 = []
    for 临时, 最终 in reversed(已完成):
        try:
            if 最终.exists():
                最终.rename(临时)
        except OSError as e:
            撤不回来.append((临时, f"回滚失败：{e}"))   # ← 记下来，别吞
    ...
    return 撤不回来      # ← 返回给调用方
```

```python
# 方案B：先抛异常，让上层决定怎么办（如果上层也无法处理，这就是正确选择）
        except OSError as e:
            raise RuntimeError(f"回滚失败：{临时} → {e}") from e
```

```python
# 方案C：如果确实想"忽略"，至少要留下痕迹
        except OSError as e:
            print(f"⚠️ 回滚失败：{临时}（{e}）")
```

**判断标准只有一条：这个错误信息，有没有到达「能做出决策的人」那里？**
没有 → 就是吞掉了。

## 问题 ②：`写日志()` 用 `"w"` —— 第二次改名覆盖第一次的日志

### 代码现状

```python
# L681
with open(日志文件, "w", encoding="utf-8") as f:
```

`"w"` 的语义是：**文件不存在就创建，存在就清空**。

### 问题在哪

`默认日志 = "改名日志.log"` 是一个**固定文件名**。

脚本跑第 1 次 → 日志里 2 行。跑第 2 次 → 日志被清空重写，现在只有 1 行。
**第 1 次那 2 行的撤销记录，永远消失了。**

而批量改名的真实使用场景恰恰是**连续多次**：
今天把这个目录的 `_v1` 改成 `_v2`，明天发现改错了要撤销——
这时候日志里已经只剩最后一次的记录了。

### 实测（本机跑出来的）

```
###### 测试5：连续两次改名，日志被覆盖 → 第一次永远撤不回来 ######
第1次改完: ['乙_v2.txt', '改名日志.log', '甲_v2.txt']
第1次日志行数: 2
第2次改完: ['丙_v2.txt', '乙_v2.txt', '改名日志.log', '甲_v2.txt']
★ 第1次的日志被覆盖了！日志现在只有: 1 行
★ 现在 --undo 只会撤销第2次，第1次改的甲_v2/乙_v2 永远回不去：
   撤销结果: [('丙_v2.txt', '丙_v1.txt')]
   撤销后目录: ['丙_v1.txt', '乙_v2.txt', '改名日志.log', '甲_v2.txt']
   ⚠️ 甲_v2.txt / 乙_v2.txt 还留在那儿 —— 第一次改名永久丢失了撤销记录
```

### 这个问题和 E24 是同一个家族

你错题本上 **E24**：「`open(path, 'w')` 会先清空再写 —— 中途失败留下 0 字节文件」
**E31**：「写目标与读源用了同一个路径变量：`open(源, 'w')` 把源数据清空」

E24/E31 是"**把源文件清空了**"，这是数据损坏。
这里是"**把撤销记录清空了**"，性质完全一样——
**`"w"` 模式永远是"覆盖"语义，用在任何"必须保留"的数据上都是错的。**

### 两种修法

| 修法 | 做法 | 适合 |
|------|------|------|
| **A. 每次一个文件** | 日志名带时间戳：`改名日志_20261115_193012.log` | 想保留历史、想撤销任意一次 |
| **B. 追加模式** | `open(..., "a")` 追加写，同一文件累积全部记录 | 想保留历史，且希望一次 `--undo` 全撤 |

**注意 B 有坑**：追加写之后，同一份日志里会混着多次操作的记录，
撤销时如果新旧名有牵连，还需要处理"A→B、B→C"这种链式——
而你的 `读日志撤销` 复用 `执行改名`（会自己分组两阶段），**这一点你的架构已经支持了**，
只需要保证日志格式一致就行。

> 💡 **更狠的 B' 方案**：撤销成功后，**把已撤销的记录从日志里删掉**。
> 这样日志永远等于"当前还有效的改名记录"，撤销天然幂等（见问题③）。

## 问题 ③：撤销不幂等 —— 第二次撤销给出误导性错误

### 代码现状

```python
# L694-742 读日志撤销
with open(日志文件, "r", encoding="utf-8") as f:
    ...
    撤销计划.append((Path(新), Path(旧)))
return 执行改名(撤销计划, "原名已被占用，无法撤销")
```

### 问题在哪

撤销成功后，**日志文件一个字都没改**。它还是原来那份「旧→新」的记录。

于是第二次撤销时：
- 日志说「`报告_v1.txt` → `报告_v2.txt`」
- 撤销计划 = 「`报告_v2.txt` → `报告_v1.txt`」
- 但 `报告_v2.txt` 已经不存在了（第一次撤销已经把它改回去了）
- 而 `报告_v1.txt` 确实存在

于是 `执行改名` 里的冲突检查命中："目标名已存在" → 报 **「原名已被占用，无法撤销」**

### 实测（本机跑出来的）

```
--- 第1次撤销 ---
成功: [('报告_v2.txt', '报告_v1.txt')] 失败: []
目录: ['报告_v1.txt', '改名日志.log']
★ 日志文件内容有没有被更新？ '...报告_v1.txt\t...报告_v2.txt'   ← 没变

--- 第2次撤销（用户手滑再点一次）---
成功: [] 失败: [('报告_v2.txt', '原名已被占用，无法撤销')]
目录: ['报告_v1.txt', '改名日志.log']
```

### 为什么这条错误信息是「误导」的

用户看到「**原名已被占用，无法撤销**」，他的第一反应一定是：

> 「谁占用了我的原名？我去看看是哪个文件把它占了。」

然后他会在目录里找，发现 `报告_v1.txt` 好好地在那儿——**没有别人占用，是它自己**。
用户会陷入困惑。

**而真实情况是：撤销已经成功了，你不需要再撤一次。**

这就是**错误信息本身是 bug**。用户按错误的提示去排查，永远查不出问题，
因为**根本没有那个问题**。

### 这条错误信息和 E40 是亲戚

你错题本上 **E40**：「返回值里放『给人看的句子』而不是『给机器判断的标识』」。

这里的症状反过来：**错误信息里放了一句『看起来合理但不符合实际情况的话』**。
给机器判断的标识（文件在不在、日志是不是已消费）被降级成了一句人话，
而这句人话**在特定场景下是错的**。

### 修法

撤销成功后，**必须让日志反映出"这批已经撤过了"**。三选一：

| 方案 | 做法 | 效果 |
|------|------|------|
| A | 撤销成功后**重写日志**，只保留没撤销成功的那些行 | 天然幂等，撤销两次 = 第二次无事可做 |
| B | 日志加状态列（`旧 \t 新 \t 已撤销`），撤销时更新状态 | 保留完整历史，可查可追溯 |
| C | 撤销前先检查「源文件（改名后的名字）是否还在」，不在就报「这批已经撤销过了」 | 最小改动，错误信息立刻变准 |

## 问题 ④：两阶段改名的回滚失败，没有报告

### 代码现状

```python
# L591-594
if 阶段2出错:
    回滚临时名(临时映射, 已完成)
    return [], 汇总组失败(组, 阶段2出错), 全局停止
```

`汇总组失败(组, 阶段2出错)` 生成的是「**这一组因为什么原因失败**」的说明。

### 问题在哪

回滚**本身**可能失败（问题①里实测过：撤不回来）。
但回滚失败的信息，**没有被加进 `汇总组失败` 的结果里**。

所以终端会显示：

```
⚠️ A.txt：目标已存在（执行中途被占了），已回滚
⚠️ B.txt：因同组文件失败，整组已回滚（本文件未改动）
```

**「已回滚」「本文件未改动」——这两句话在回滚失败时是假的。**

文件可能实际停在 `__tmp_xxxx.txt` 上。用户看到「已回滚」，就不会再去检查这个目录，
**结果就是一批文件静静地躺在临时名上，永远没人管**。

### 修法

```python
if 阶段2出错:
    撤不回来 = 回滚临时名(临时映射, 已完成)      # ← 接收返回值
    失败 = 汇总组失败(组, 阶段2出错)
    for 名, 原因 in 撤不回来:                      # ← 追加进去
        失败.append((名, f"回滚失败，需人工处理：{原因}"))
    return [], 失败, 全局停止
```

# 二、异常处理的核心：捕获之后的「三段决策」

11-08 我给你讲过四条原则。其中最有用的一条是：

> **捕获要放在「能做出正确决策」的那一层。**

但这条原则只说了**在哪里捕获**，没说**捕获之后要干什么**。

今天补上后半段。你现在的代码之所以有上面 4 个 bug，
根因都是同一个：**只做了「捕获」，没做「决策」和「上报」。**

## 异常处理的完整流程是三段

```
      异常抛出
         │
    ┌────▼─────────────────────────────┐
    │ 第 1 段：捕获（Where）            │  ← 11-08 讲过：放在能决策的那层
    │   try/except，在哪一层 try        │
    └────┬─────────────────────────────┘
         │
    ┌────▼─────────────────────────────┐
    │ 第 2 段：决策（What）             │  ← 今天新增：捕获之后做什么
    │   三个选项，只有一个是对的：      │
    │   ① 局部失败 → 记录 + 继续       │
    │   ② 全局失败 → 停止 + 报告       │
    │   ③ 无法处理 → 重抛（包装/原样） │
    └────┬─────────────────────────────┘
         │
    ┌────▼─────────────────────────────┐
    │ 第 3 段：上报（Who）             │  ← 今天新增：处理完怎么让人知道
    │   信息必须到达「能决策的人」      │
    └──────────────────────────────────┘
```

**你代码里的 4 个 bug，全部是第 3 段缺失。**
第 1 段（捕获）你做得很好，第 2 段（决策）也基本到位——**唯独第 3 段到处漏。**

## 第 2 段：三个决策选项，怎么选

### 选项 ①：局部失败 → 记录 + 继续

**适用**：这个错误只影响这一个文件，其他文件无关。

**你的代码已经做对了**，比如：

```python
except PermissionError:
    失败.append((旧, "文件被其他程序占用，已跳过"))
    # ← 记录了，而且没有 break，继续下一个
```

注意它同时满足了三件事：
- 记下来了（进 `失败` 列表）
- 继续了（没有 break）
- 上报了（`main()` 最后会遍历 `失败` 打印出来）

### 选项 ②：全局失败 → 停止 + 报告

**适用**：这个错误说明**环境本身出问题了**，继续做只会让更多文件受损。

**你的代码也已经做对了**，这是 11-10 新加的亮点：

```python
except OSError as e:
    if e.errno == errno.ENOSPC:  # 磁盘满
        失败.append((旧, "磁盘已满（全局错误），已停止"))
        全局停止 = True
        break                      # ← 跳出整个循环，不是 continue
```

而且 `main()` 里还专门算了「未处理」的数量并提示：

```python
未处理 = len(计划) - len(成功) - len(失败)
print(f"⛔ 因全局错误【提前中止】：还有 {未处理} 个文件没有处理")
```

**这个「未处理」的计算是个聪明设计**，值得表扬。

### 选项 ③：无法处理 → 重抛

**适用**：这个错误我根本不知道怎么办，交给上层。

```python
except OSError as e:
    raise RuntimeError(f"批量改名失败：处理 {旧.name} 时出错") from e
```

`from e` 是关键——它把**因果链**保留下来。

## `from e` 到底有什么用（实测对比）

```
###### 知识点验证2：raise ... from e 的因果链 ######
外层异常: 批量改名失败：处理文件 X 时出错
__cause__ : ValueError('原始错误：磁盘满了')
★ 有 from e → 因果链完整，报错时能同时看到根因

没有 from e → __cause__ : None
★ 根因变成了 'During handling of the above exception...'，链条被割裂
```

**没有 `from e`** 时，Python 会打这么一长串：

```
Traceback (most recent call last):
  File "外层.py", line 5, in 外层
    内层()
  File "内层.py", line 2, in 内层
    raise ValueError("原始错误：磁盘满了")
ValueError: 原始错误：磁盘满了

During handling of the above exception, another exception occurred:
  ...
RuntimeError: 批量改名失败：处理文件 X 时出错
```

两段堆栈连在一起。**有 `from e`** 时，Python 直接给你画一条链：

```
ValueError: 原始错误：磁盘满了

The above exception was the direct cause of the following exception:
  ...
RuntimeError: 批量改名失败：处理文件 X 时出错
```

**"The above exception was the direct cause"** —— 一眼看出谁导致了谁。

### 第 3 段：上报——今天的主角

前面两段你基本做对了。第三段是今天要重点讲的。

**判断标准只有一条**：

> **这个错误信息，有没有到达「能做出决策的人」那里？**

「能做出决策的人」是谁？取决于场景：

| 场景 | 决策人是谁 | 上报形式 |
|------|-----------|---------|
| 批量改名（终端） | **用户本人**（在屏幕前） | print + 失败清单 |
| 库函数 / 项目模块 | **调用方**（另一个函数） | return 值 / raise |
| 长时间任务 | **之后的自己**（下次排查） | 写日志文件 |

你的 `回滚临时名()` 属于第三种里最糟的一种：
**谁都没上报**——用户不知道、调用方不知道、以后的自己也不知道。

### 三种上报姿势

```python
# 姿势1：返回给调用方（最推荐，适合库函数）
def 回滚临时名(...):
    撤不回来 = []
    ...
    except OSError as e:
        撤不回来.append((临时, str(e)))
    return 撤不回来

# 姿势2：抛出去（适合「我处理不了」）
    except OSError as e:
        raise RuntimeError(f"回滚失败：{临时}") from e

# 姿势3：打印（适合脚本，简单直接）
    except OSError as e:
        print(f"⚠️ 回滚失败：{临时}（{e}）")
```

**姿势1 优于姿势3**，因为你打印完就忘了，
而返回的列表还能被合并进总的失败报告——用户最终能看到一条完整的失败清单。

# 三、Python 异常层级：什么时候该抓哪个

11-08 讲过一遍层级图。今天要补的是**「实战怎么选」**。

## 完整层级（带 errno）

```
BaseException
├── Exception                        ← 常规错误，都该捕获
│   ├── ValueError                   ← 值不对：int('abc')、int('') 
│   ├── TypeError                    ← 类型不对：len(5)、'a' + 1
│   ├── KeyError                     ← 字典里没这个 key
│   ├── IndexError                   ← 列表越界
│   ├── FileNotFoundError   errno=2  ← ENOENT
│   ├── FileExistsError     errno=17 ← EEXIST
│   ├── PermissionError    errno=13/16 ← EACCES / EBUSY
│   └── OSError                       ← 上面三个的父类
│       ├── FileNotFoundError
│       ├── FileExistsError
│       ├── PermissionError
│       └── ...（还有 20 多个）
├── KeyboardInterrupt                ← Ctrl+C，【不该捕获】
└── SystemExit                       ← sys.exit()，【不该捕获】
```

## 三个实战要点

### 要点 1：异常类型和 errno 是两个维度

这是你 11-10 新代码里最值得表扬的设计，但很多人不知道：

```python
except OSError as e:
    if e.errno == errno.ENOSPC:    # 28 = 磁盘满
    if e.errno == errno.EROFS:     # 30 = 只读文件系统
```

| 维度 | 回答的问题 | 例子 |
|------|-----------|------|
| **异常类型** | 哪一类？ | `PermissionError` |
| **errno** | 具体为什么？ | `EACCES=13`（权限不足）vs `EBUSY=16`（文件被占用） |

实测数据：

```
PermissionError  OSError子类=True
errno.ENOENT=2  EEXIST=17  EACCES=13  EBUSY=16  ENOSPC=28
```

**同一个 `PermissionError`，errno 不同，处理方式可能完全不同**：
- `EACCES`（权限不足）→ 跳过这个文件，继续
- `EBUSY`（文件被占用）→ 跳过这个文件，继续（但提示用户关掉占用的程序）

而 `ENOSPC`（磁盘满）→ **全局停止**。

所以**光有异常类型不够，得配合 errno**。你代码里 ENOSPC/EROFS 用 errno 判断，
FileNotFoundError/FileExistsError 用类型判断——**这个混用是完全正确的做法**。

### 要点 2：`Path.rename` 和 `os.replace` 在 Windows 上行为不同（实测）

这条对批量改名特别重要：

```
###### 知识点验证1 ######
Path.rename → FileExistsError | errno = 17 | 当文件已存在时，无法创建该文件。
  b.txt 内容还在吗？ 原文件B          ← 没被覆盖
os.replace → 成功覆盖！d.txt 内容现在是: 原文件C   ← 被静默覆盖了！
```

| 方式 | 目标已存在时（Windows） | 危险度 |
|------|----------------------|--------|
| `Path.rename()` | 抛 `FileExistsError`，**拒绝覆盖** | ✅ 安全 |
| `os.replace()` | **静默覆盖**，原文件内容直接没了 | 🔴 危险 |

**你脚本用的是 `Path.rename()`——正确。**
这也是为什么你的脚本要**自己先查 `新.exists()`**：
不是因为 rename 会覆盖，而是因为**跨平台行为不一致**，
你必须自己在两个平台上都保证"绝不覆盖"。

> 📌 **顺带一个你可能会遇到的坑**：如果你哪天在 todo-cli 里用 `os.replace` 做"原子写入"，
> 那个场景下覆盖是**故意的**（新内容替换旧内容），所以是对的。
> **但同样的写法放进批量改名就是灾难。**
> **同一个 API，在不同场景下，一个是对的，一个是错的。**

### 要点 3：异常类型不匹配 = 捕获不到 = 静默崩溃

你错题本上 **E30**：「ValueError vs TypeError 分不清：except 写错类型就接不住」。

```python
try:
    x = int("abc")
except KeyError:        # ← 接不住！ValueError 不是 KeyError 的子类
    print("出错了")
# → ValueError 照样往上抛，程序崩溃
```

**except 写错类型的后果不是"漏掉一个分支"，是"异常穿透到上层"。**
在批量改名脚本里，这意味着一个本该被"跳过并记录"的文件，
直接让整个程序带着 traceback 崩掉。

# 四、四个原理，换成新说法

11-08 的四条原则，今天用新例子重讲一遍（例子全换新的）。

## 原理 ①：不要裸 `except:`

**上次说的是**：裸 except 会把 `int('abc')` 的 ValueError 吞掉然后返回 -1（E15 静默错误）。

**今天的新说法**：裸 except 还会**吃掉你根本不该吃的东西**。

```python
try:
    处理文件(f)
except:              # ← 这个 except 会捕获 BaseException 的所有子类
    print("失败")
```

包括：
- `KeyboardInterrupt`（用户按了 Ctrl+C）→ **你把用户的取消操作吃掉了**，程序继续跑
- `SystemExit`（`sys.exit()` 触发的）→ **你把程序退出吃掉了**，程序继续跑

**Ctrl+C 被吃掉是批量脚本最恶心的 bug**：用户狂按 Ctrl+C 想停下来，
程序不理他，继续改文件。**用户失去了最后的控制权。**

```python
# ✅ 正确：要么写具体类型，要么至少写 Exception
except Exception as e:      # 不吃 Ctrl+C，不吃 SystemExit
except (ValueError, TypeError) as e:   # 更精确
```

> 📌 **实测提醒**：`except Exception` **捕不到** `KeyboardInterrupt`——
> 因为 `KeyboardInterrupt` 是 `BaseException` 的直接子类，不是 `Exception` 的子类。
> 这不是 bug，是设计：Ctrl+C 必须能穿透你的业务代码。

## 原理 ②：捕获要放在能做出决策的那一层

**上次说的是**：循环外捕获 3 个文件只改 1 个，循环内捕获改 2 个。

**今天的新说法**：**"决策"要分两种，同一层里做不了就得分层。**

| 决策类型 | 例子 | 放哪 |
|---------|------|------|
| **这个文件怎么办** | 权限不足 → 跳过它 | 循环内 |
| **这批文件怎么办** | 磁盘满 → 全部停止 | 循环内也要能 break 到外层 |
| **这个程序怎么办** | 目录不存在 → 退出 | 最外层 |

你的代码里 `main()` 的参数检查就是"第三层决策"：

```python
if not 目录.exists():
    print(f"❌ 目录不存在：{目录}")
    return                       # ← 程序级决策
```

**层级清楚了，代码自然清楚。** 这就是为什么「异常处理写得好不好」，
本质上是「代码的分层清不清晰」——不是玄学。

## 原理 ③：`try` 的范围要小

**上次说的是**：try 包太多，"磁盘满"和"文件被占用"会被当成同一回事。

**今天的新说法**：**try 范围大，还有一个隐蔽的副作用——你会 catch 到不是你想要的那个异常。**

```python
# ❌ try 包太大
try:
    数据 = 读文件(p)          # ← 这里可能抛 FileNotFoundError
    结果 = 处理数据(数据)      # ← 这里可能抛 ValueError
    写文件(p, 结果)            # ← 这里可能抛 PermissionError
except PermissionError:
    失败.append((p, "权限不足"))
# → 文件不存在时，FileNotFoundError 穿透了整个 try
# → 而且你没法区分"读失败"和"写失败"
```

```python
# ✅ try 只包住那一个会抛你想抓的异常的操作
try:
    结果 = 处理数据(数据)
except ValueError as e:
    失败.append((p, f"数据处理失败：{e}"))
```

**规则**：`try` 块里只放**可能抛你要抓的那个异常**的那几行。

## 原理 ④：捕获后必须处理或重抛，不能吞

**上次说的是**：三种正确姿势（记下来+继续 / raise 重抛 / raise 包装后重抛）。

**今天的新说法**：这三种姿势有一个**共同的检验标准**——
**处理完，这个错误的信息去哪了？**

| 姿势 | 信息去哪了 | 检验 |
|------|-----------|------|
| 记下来 + 继续 | 进了失败列表 → 最终会被打印 | ✅ 信息到达用户 |
| raise 重抛 | 沿着调用栈往上走 | ✅ 最终有人接 |
| raise 包装后重抛（`from e`） | 同上，且保留因果链 | ✅ 信息最完整 |
| ~~`pass`~~ | ~~** nowhere **~~ | ❌ **信息蒸发** |

**`pass` 不是「优雅地忽略」，是「把错误信息扔进垃圾桶还盖上盖子」。**

只有一种情况 `pass` 是对的：**这个错误确实无关紧要，且你在别处已经处理过了**。
比如：

```python
try:
    os.remove(临时文件)
except FileNotFoundError:
    pass    # ← 这个是【清理临时文件】，删不掉就无所谓，本来就不存在
```

**判断方法**：问自己「如果这里失败了，用户会少拿到什么 / 多留下什么？」
答不上来 → 你在吞错误。

---

## 今天的核心一句话

> **异常处理不是「捕获异常」，是「让每个错误都到达该到的人手里」。**
>
> 捕获是手段，上报才是目的。
> 一个不崩溃、不报错、退出码 0、但结果不对的程序，
> 比一个直接崩掉的程序**危险十倍**——
> 因为崩掉的程序你一定会去修，而"看起来正常"的程序，你会信它。

## 附：今天新增的知识点速查

| 知识点 | 一句话 |
|--------|--------|
| 异常处理三段 | 捕获（Where）→ 决策（What）→ 上报（Who），第三段最容易漏 |
| errno | 异常类型说"哪一类"，errno 说"具体为什么"，两者正交 |
| `raise X from e` | 保留因果链，报错时能直接看出谁导致谁 |
| `Path.rename` vs `os.replace` | 前者拒绝覆盖（安全），后者静默覆盖（危险） |
| 幂等 | 同一个操作做两次 = 做一次。撤销必须幂等 |
| 错误信息本身也是 bug | 报一句不成立的话，比不报错更浪费用户时间 |
